Deploy to Azure — End-to-End

Noble Invoice Processor · decision-engine Function + Content Understanding analyzer

remote build: on deploy subpath: functionapp runtime: Python v2

Two things deploy separately. The Function code (the 8-digit PO/job gate rides along with it) and the CU analyzer (the 8-digit prompt — a data-plane change that must be re-provisioned). Do both. Your .vscode/settings.json sets scmDoBuildDuringDeployment: true, so Azure rebuilds from requirements.txt server-side (the new tzdata installs automatically). local.settings.json is never deployed — the app reads its config from Azure Application Settings.

Replace these placeholders throughout: <APP> (Function App name), <RG> (resource group), <HOST> (default host name), <KEY> (function key).

1Re-provision the CU analyzer (the prompt)

Editing analyzers\create-generalinvoice-analyzer.json changes nothing live — it must be pushed to CU. A push to the prod generalinvoice id is now gated: create_analyzer.py refuses unless a green golden-corpus regression stamp exists for the current clean HEAD. So the order is commit → regress.py → create_analyzer.py.

# Both scripts take --load-local-settings: they seed the CU endpoint + key (the same values the
# Function uses) from functionapp\local.settings.json when those env vars are unset. Needed on this
# machine because the TLS inspector blocks every az-login / DefaultAzureCredential token path, so the
# CU key is the only working auth. Nothing is printed; the key never leaves local.settings.json.

# 1a. Golden-corpus regression -> must be PASS; a green run on a clean HEAD writes
#     out\regress\<sha>.json (the stamp the push gate requires). ~1s on a cache hit;
#     real CU calls only when the analyzer prompt actually changed.
.\.venv\Scripts\python.exe scripts\regress.py --load-local-settings

# 1b. Push the prod analyzer (key auth via --load-local-settings; gate passes because the stamp exists)
.\.venv\Scripts\python.exe scripts\create_analyzer.py --load-local-settings

Expect Prod push gate: green regression stamp found… then Done. analyzer_id=generalinvoice…. This overwrites the live generalinvoice analyzer (allow_replace=True). Auth is the CU key that --load-local-settings seeds: create_analyzer.py uses AZURE_CU_KEY when set and otherwise falls back to DefaultAzureCredential. On this machine that fallback always fails — DefaultAzureCredential failed to retrieve a token from the included credentials, because the TLS inspector blocks az-CLI / PowerShell / IMDS token acquisition. That is a different failure from request-TLS (which truststore already handles), so the fix is the key, not --insecure. In Azure the app runs as its managed identity over AAD and needs Cognitive Services User on invoice-processing-dev-resource.

Gate escapes & TLS. Pass --force to create_analyzer.py only for an emergency (e.g. a roll-back) where you accept skipping the regression. Both scripts inject truststore so they verify through the corporate TLS inspector automatically — no --insecure and no wrapper needed. A scratch/test push (--analyzer-id generalinvoicescratch) is never gated. The router (--file analyzers\create-router-analyzer.json --analyzer-id invoicerouter) deploys separately and only when it changed.

2Deploy the Function code

Prerequisite on this machine — func needs the az shim, not the profile wrapper. func shells out to az for authentication and app lookup, and it does so from a child process. The truststore fix is a PowerShell function, which lives only inside the PowerShell process and is invisible to children — so func gets the raw az.cmd, which fails TLS behind the inspecting proxy. The symptom is misleading: Can't find app with name "func-invoiceprocess-westus" or Unable to connect to Azure. The app is fine; func simply could not enumerate it.

The fix is a .cmd on PATH (a file is visible to child processes), installed at %LOCALAPPDATA%\az-truststore\shim\az.cmd and prepended to the user PATH. Verify before deploying — and note that az account show proves nothing, because it only reads the local token cache: 
az account get-access-token --query expiresOn -o tsv   # must succeed

Option A — Core Tools (CLI)

cd "C:\Users\georg\dev\Noble Homes\Invoice Extractor\noble-invoice-process\functionapp"
$APP= "func-invoiceprocess-westus"
$RG = "rg-content-understanding-dev"
func azure functionapp publish $APP --build remote
Expect to retry. Even with the shim, ARM calls through the TLS inspector drop intermittently with ConnectionResetError 10054 — measured at 1 success in 8 during the 2026-08-18 deploy, while succeeding on the first try an hour earlier. func makes its app-lookup call with no retry, so a dropped connection surfaces as Can't find app with name. That message means "try again", not "wrong app name". Loop it: 
$deployed = $false
for ($i = 1; $i -le 8; $i++) {
    "--- publish attempt $i ---"
    func azure functionapp publish $APP --build remote | Tee-Object -Variable log
    if (($log -join "`n") -match 'The deployment was successful') { $deployed = $true; break }
    "attempt $i did not land - retrying"
}
if (-not $deployed) {
    Write-Warning "8 attempts with no success line - check the portal before publishing again"
}
The publish itself is idempotent, so a retry after a partial failure is safe.
⚠ Loop on the success string, never on the exit code. This snippet previously read if ($LASTEXITCODE -eq 0 -or $?) { break }, which is broken: func exits non-zero even when the deploy succeeds (see the trailing-SSL-error note below), so that loop never breaks and re-publishes up to 8 times — on a runtime change, holding the outage open for every one of them. Corrected 2026-08-20. Note also that 2>&1 is deliberately absent: PowerShell 5.1 wraps native stderr in ErrorRecords and would corrupt the match. If you are at the keyboard, a single un-looped func azure functionapp publish $APP --build remote is safer still — just read the log.
Two things that look like failures and are not.
  • A trailing SSL error after The deployment was successful! — func fetches the invoke URLs as its last step and that call goes through the inspector. The deploy already landed; the process still exits non-zero. Read the log, not the exit code.
  • Remote build for Python 3.14 is not yet supported for Flex — a stale, non-blocking warning printed by Core Tools 4.12.0. The remote build runs and succeeds; observed on the 2026-08-20 deploy, where Oryx completed and the app came up on 3.14. Upstream fixed remote build on 2026-06-23 (Azure/azure-functions-python-worker#1801); only the warning string lingered. It is gone in Core Tools 4.13.0 — which winget does not yet serve (it offers 4.12.1), so don't chase the upgrade, and especially not right before a deploy.
The app runs Python 3.14 as of 2026-08-20. Local and cloud now match, so the old Local python version '3.14.x' is different from '3.13' mismatch warning no longer appears. The former "stay on 3.13, Flex has no remote-build support" rule is retired: 3.14 is GA on Flex with EOL Oct 2030. Full runbook, including the outage window and rollback: docs/python-314-migration.html.

Analyzer before code — not just a preference this release. When a release renames or adds an extracted field, deploying the Function before re-provisioning the analyzer makes the new code read a field the live analyzer doesn't emit yet. The 2026-07-24 release renamed invoice_date → invoice_date_extract and added invoice_date_generate, so shipping this code against the old analyzer would default every invoice to today's date until Step 1 lands. Always finish Step 1 before Step 2.

Identity / RBAC — the part az login can't simulate (production runs as the managed identity, not you). The app's identity id-invoice-processing-dev must have Cognitive Services User on the CU resource, Storage Table Data Contributor on stinvoicedevwestus, and (since 2026-07-14) Storage Blob Data Owner on stinvoicefuncdevwestus — host + deployment storage are identity-based (AzureWebJobsStorage__accountName/__credential/__clientId; no storage connection strings anywhere). Leave AZURE_CU_KEY and AZURE_TABLES_CONNECTION_STRING unset to stay keyless, and never add an AzureWebJobsStorage connection-string setting (local's UseDevelopmentStorage=true included) — it would override the keyless host storage.

4Get the base URL + function key

# Base URL — Flex apps get a HASHED default host name; the bare <APP>.azurewebsites.net does NOT resolve
az functionapp show -g $RG -n $APP --query "defaultHostName" -o tsv   # -> <APP>-<hash>.westus-01.azurewebsites.net

# Function key (route auth_level is FUNCTION)
az functionapp keys list -g $RG -n $APP --query "functionKeys.default" -o tsv

Call these <HOST> and <KEY>. On this machine the az functionapp … commands can die on TLS-inspector resets (10054) — retry in a loop before reaching for a fallback, since the failure is transient rather than a permission or naming problem (the key below came back on attempt 5 of 6 on 2026-08-18):

$k = $null
for ($i=1; $i -le 6 -and -not $k; $i++) {
    $k = az functionapp keys list -g $RG -n $APP --query "functionKeys.default" -o tsv 2>$null
}

If it still will not come, fall back to the portal (Overview → Default domain; App keys) or the ARM REST recipe in docs/ai/troubleshooting.md. All keys minted before 2026-07-14 are invalid (host storage was replaced). Treat the key as a secret: keep it out of command output and shell history, and delete any file you stage it in.
