1 · Problem and algorithm class

The CU extractor produces a service_address string per invoice. It must be resolved to a Dataverse property record (~50,000 managed properties: houses and condo units) so the invoice write carries the correct property lookup. Extracted addresses frequently omit postal code and city, vary in abbreviation and word order, and include Vancouver-specific forms (unit-hyphen-civic prefixes, civic ranges, HSE designators, French Quebec formats).

Rejected approaches, for the record: text embeddings (underweight digits — 123 Main and 125 Main embed nearly identically; a confident wrong-property auto-write is worse than a review exception); LLM-as-matcher (non-deterministic, violates the scorecard-validation discipline protecting the auto-write path); Dataverse relevance search (edit-distance fuzziness treats digit substitutions as minor; index behavior not versioned with code, not offline-testable); libpostal (~2 GB model data — deployment size and cold-start cost on Flex Consumption, overkill for a bounded reference set).

Chosen approach: deterministic normalize → block → filter → score record linkage against a snapshot of the property master, implemented as a new gate in the existing gate layer. Pure Python, no Azure dependencies in the matching logic, fixture-testable offline, thresholds governed by POLICY_VERSION.

3 · Architecture

50K rules out fetch-per-invocation from Dataverse (latency, throttling) and row-by-row Table Storage reads at load (~50 paged round trips). It does not rule out in-memory matching: ~50K canonicalized records is 10–15 MB. The design splits into an offline snapshot pipeline and a runtime gate with a per-instance memory cache.

┌─ SNAPSHOT PIPELINE (nightly, timer trigger) ──────────────────────────┐ │ │ │ Dataverse property table ──paged fetch──► address_norm.py │ │ (~50K records) canonicalize + index keys │ │ RANGE EXPANSION (A2) │ │ │ │ │ ▼ │ │ stinvoicedevwestus / blob container │ │ property-snapshot/current.json.gz │ │ (~2–4 MB gz; metadata: version, count, │ │ POLICY_VERSION of normalization rules) │ └───────────────────────────────────────────────────────────────────────┘ ┌─ RUNTIME (per invoice, inside func-invoiceprocess-westus) ────────────┐ │ │ │ CU extraction ─► existing gates ─► HAPPY_PATH_CANDIDATE only │ │ │ │ │ ▼ │ │ B6: COMPOUND SPLIT (A1) ─► normalize each component (address_norm) │ │ │ │ │ ├─ BLOCK exact street_number / range overlap → candidates │ │ ├─ FILTER unit rules (exact-or-nothing on numeric digits; │ │ │ soft designators A3) + directional hard filter (A4) │ │ ├─ SCORE rapidfuzz token_set_ratio on street name; │ │ │ city / postal as confirmers only, never required │ │ └─ ROUTE MATCHED ─► attach property_id ─► Dataverse write │ │ else ─► REVIEW_B6_ADDRESS_MATCH (+ reason code) │ │ │ │ Snapshot cache: module-level; TTL 15 min; etag HEAD check on expiry │ └───────────────────────────────────────────────────────────────────────┘

3.1 · Snapshot pipeline

  • Owner: new timer-triggered function sync_property_snapshot in the same Function App (nightly, 09:00 UTC = 01:00 PST). Keeping it in-app means address_norm.py is one shared module used identically at snapshot build and at runtime — the two sides cannot drift, which is the classic failure mode of record-linkage systems.
  • Dataverse access: reuses the access path B5 already exercises. Paged fetch: record ID, address line(s), unit field, city, postal code.
  • Output: one gzipped JSON blob property-snapshot/current.json.gz in a new blob container in stinvoicedevwestus. Table Storage remains ledger-only. Each record: raw source values + canonical components + block keys. Blob metadata: snapshot_version (UTC timestamp), record_count, POLICY_VERSION of the normalization rules that produced it.
  • Sanity gate on write: refuse to overwrite if the new record count drops >5% vs. the previous snapshot (protects against a partial Dataverse fetch silently shrinking the reference set). Failure leaves the previous snapshot in place, logs an error.

3.2 · Runtime cache

  • Module-level cache: parsed snapshot + blocking index, built once per instance. TTL 900 s; on expiry, blob HEAD compares etag; reload only on change. Within one invocation the snapshot is fixed — an invoice is never matched against two snapshot versions.
  • Snapshot unavailable at cold start → fail the invocation (HTTP 500). Power Automate retry policy handles it. Do not route to review: that floods the queue with exceptions that have nothing to do with the invoice. Infrastructure failure ≠ document exception.
  • Ledger records snapshot_version per invoice — every match decision is reconstructable against the exact reference set it used.

4 · Canonicalization spec (address_norm.py)

Rule-based, pure Python, table-driven. Output components per address component:

{
  "unit":            "501" | "HSE" | null,   # numeric units and designator-only units (A3)
  "unit_is_soft":    true | false,           # true when unit is a designator with no number (A3)
  "civic_start":     6682,                   # integer; exact-match key, never fuzzy
  "civic_end":       6690,                   # == civic_start unless a civic range (A2)
  "street_name":     "FRASER",               # canonical tokens, type/directional stripped out
  "street_type":     "ST" | null,            # Canada Post canonical abbreviation
  "directional":     "W" | null,             # N,S,E,W,NE,NW,SE,SW (French mapped: O→W …)
  "city":            "VANCOUVER" | null,
  "postal":          "V6B1A1" | null         # A1A1A1, space stripped
}

4.1 · Rules

  1. Case / accents / punctuation: uppercase; strip accents (MONTRÉAL → MONTREAL); collapse punctuation and whitespace. Commas are treated as component separators, not address separators.
  2. Compound splitter A1: before parsing, split the string on &, word-bounded AND, and ; into sub-address components. Each component is parsed independently. Matching semantics in §5.5.
  3. Province stripping A5: trailing two-letter province tokens (BC, AB, SK, MB, ON, QC, NB, NS, PE, NL, YT, NT, NU) are recognized and removed before city extraction.
  4. Unit extraction — suffix forms: UNIT 501, #501, APT 501, SUITE 501, STE 501, APP 501, BUREAU 501 → unit=501.
  5. Unit extraction — designator table A3: HSE (house), BSMT, MAIN, LWR/LOWER, UPPR/UPPER, PH, TH, RM, FL. A designator followed by a number → normal unit (PH 2 → unit=PH2). A designator with no number → unit=<designator>, unit_is_soft=true. HSE is BC/Vancouver practice for distinguishing the principal house from a secondary/laneway unit at the same civic number.
  6. Hyphen disambiguation A2 — the same surface form means two things. Canada Post places a unit number before the civic number with a hyphen (501-123 MAIN ST = unit 501 at 123 Main); civic ranges (6682-6690 FRASER ST = building spanning 6682–6690) use an identical hyphen. Rule, applied when both segments are numeric and a street token follows:
    • Range iff first < second AND (second − first) ≤ 30 AND same parity → civic_start/civic_end set to the pair, no unit.
    • Unit–civic iff first > second, OR delta > 30, OR parity differs → unit=first, civic_start=civic_end=second.
    • Ambiguous (e.g. 101-105 MAIN: ascending, delta 4, same parity — could be either): heuristic says range; if the resulting parse yields zero candidates, the parser retries under the unit–civic interpretation; if both interpretations yield candidates for different properties → review, UNPARSEABLE_ADDRESS. Never guess between two live interpretations.
    • Non-numeric first segment: designator table (rule 5) or, if unrecognized, review UNPARSEABLE_ADDRESS.
  7. Street type table: Canada Post canonical abbreviations both directions — STREET/ST, AVENUE/AVE/AV, BOULEVARD/BLVD/BOUL, DRIVE/DR, CRESCENT/CRES, ROAD/RD, PLACE/PL, COURT/CRT/CT, TERRACE/TER, WAY, LANE, plus French types RUE, CHEMIN/CH, CÔTE, MONTÉE, RANG. Street type is nullable (BROADWAY has none).
  8. French word order: Quebec places the type before the name (123 RUE PRINCIPALE). Parser recognizes type-first and type-last patterns; both emit identical components.
  9. Directionals: English N/S/E/W + combos; French O/OUEST→W, E/EST→E, N/NORD→N, S/SUD→S. Prefix (W BROADWAY) and suffix (BROADWAY W) forms both emit directional=W — storage as a separate component makes word order irrelevant.
  10. Postal: validate [A-Z]\d[A-Z]\s?\d[A-Z]\d; store space-stripped; anything else → null. Never guess.
  11. Ordinals: 1ST/1ERE/1RE → 1, 2ND/2E → 2, 51ST → 51, etc., so E 51ST AVE and EAST 51 AVENUE canonicalize identically.
Every rule above is table-driven data inside address_norm.py, versioned under POLICY_VERSION in field_policy.py. A rule change bumps the version; a snapshot whose metadata carries a different POLICY_VERSION than the running code fails loudly at load and forces a resync — rule versions are never silently mixed.

5 · Blocking, filtering, scoring

5.1 · Blocking index (built at snapshot load)

index:      dict[civic_number → list[property]]     # primary block, exact integer key
multi_unit: dict[(civic_number, street_name) → count of managed units]

Range expansion A2: a master record stored as a civic range (6682-6690 FRASER ST) is indexed under every same-parity civic number in the range (6682, 6684, 6686, 6688, 6690 → same property). Tenant invoices routinely cite their storefront number, not the building's full range; without expansion, 6684 FRASER ST would find nothing. Invoice-side ranges block on civic_start; a candidate qualifies when the integer ranges overlap.

At 50K properties a common civic number yields at worst a few hundred candidates — microseconds of scoring. Digits are never fuzzy-matched. 123 MAIN ST can never match 125 MAIN ST; a wrong-property auto-write is strictly worse than a review exception.

5.2 · Candidate filtering — unit rules (incl. A3)

5.3 · Candidate filtering — directional hard filter A4

Directionals are digit-class signals, not fuzzy text: E 51ST and W 51ST are opposite ends of the city, yet token_set_ratio("BROADWAY W","BROADWAY E") ≈ 90 — above the review floor and near the accept threshold. Rule: when both sides carry a directional and they differ → exclude the candidate outright. Either side missing a directional → no penalty (confirmer philosophy preserved). This removes directionals from the fuzzy-score surface entirely.

5.4 · Scoring

  • rapidfuzz.fuzz.token_set_ratio(invoice.street_name_full, candidate.street_name_full) where street_name_full = canonical name + type tokens (directionals excluded — they are handled by A4). Score 0–100. rapidfuzz is C/Python, deterministic, version-pinned, offline-testable.
  • Confirmers, never requirements (this is what makes missing city/postal a non-event): postal exact match → +4; city exact match → +2; postal present on both sides and mismatched → −15 (hard contradiction). Capped at 100.
  • Candidates sorted by (score DESC, property_id ASC) — the tiebreak makes ordering fully deterministic.

5.5 · Compound semantics A1

When the splitter (rule 4.1-2) yields multiple components (6682-6690 FRASER ST & 707 E 51ST AVE — a two-frontage corner building), each component runs the full block → filter → score pass independently. Decision:

  • All components parse AND all resolve (per §6 accept criteria) AND all agree on one property_id → MATCHED to that property.
  • Components resolve to different properties → REVIEW · COMPOUND_MISMATCH (reviewer decides: shared-service invoice, or which property).
  • Any component fails to parse or resolve → REVIEW with that component's reason. Agreement cannot be confirmed, so no match is issued. Conservative by construction.

7 · Pipeline placement and enum

  • Routing enum becomes five values: HAPPY_PATH_CANDIDATE, REVIEW_B4_CRITICAL_FIELD, REJECT_B2_OTHER_CATEGORY, REVIEW_NO_CHILD_EXTRACTION, REVIEW_B6_ADDRESS_MATCH.
  • B6 runs only on documents that survive existing gates as HAPPY_PATH_CANDIDATE — no value in matching addresses on documents already headed to review or rejection.
  • Gate layer stays free of Azure service dependencies: gates.py receives the candidate list and snapshot metadata as plain inputs; blob load and cache live in property_reference.py, mirroring how B5's Dataverse query sits outside the pure gate logic.
  • Approval path: for invoices that entered review, the human reviewer confirms or selects the property in the review UI — B6 is not re-run at approval (the human decision supersedes the score). B5 dedup re-run at approval is unchanged.

8 · Function response contract (additive)

"property_match": {
  "status": "MATCHED" | "REVIEW",
  "reason": null | "NO_CANDIDATE" | "LOW_SCORE" | "AMBIGUOUS_MULTI"
                 | "AMBIGUOUS_UNIT" | "UNPARSEABLE_ADDRESS"
                 | "COMPOUND_MISMATCH",
  "property_id": "guid-or-null",
  "score": 96,
  "snapshot_version": "2026-07-01T09:00:12Z",
  "candidates": [                      // top 3, only when status = REVIEW
    { "property_id": "...", "score": 88, "display_address": "..." }
  ]
}
  • Power Automate uses property_id as the lookup value in the Dataverse invoice write on the happy path.
  • candidates pre-populates the reviewer's pick-list in the SharePoint queue — the human disambiguates from a shortlist instead of searching 50K properties. Deterministic output, not an LLM assist.
  • Ledger gains: b6_status, b6_reason, matched_property_id, b6_score, snapshot_version.

11 · Test plan

  1. Fixture snapshot: synthetic property-snapshot JSON in scripts/fixtures/ — engineered to include multi-unit condo buildings, near-miss civic numbers (123 vs 125), the same street name in two cities, civic-range commercial records, HSE/laneway pairs at one civic number, opposite-directional street pairs, French Quebec addresses, ordinal streets.
  2. test_address_norm.py: table-driven canonicalization — every abbreviation, unit suffix form, designator, hyphen classification (range / unit–civic / ambiguous-with-retry), compound split, province strip, French pattern, ordinal, postal validation. The four §10 strings verbatim. Target ≈ 80–100 checks.
  3. test_gate_b6.py: end-to-end match cases against the fixture snapshot — one per routing-table row (§6), plus: missing postal (must match), postal contradiction (must penalize), margin tie (must review), unit-absent multi-unit (must review), 123-vs-125 (must NOT match), directional contradiction (must exclude, A4), storefront-number-within-master-range (must match, A2), compound agree / compound disagree (A1), soft-designator sole-record / multi-record (A3).
  4. Determinism check: run the full case set twice; assert byte-identical results including candidate ordering.
  5. Scorecard: extend step24_scorecard.csv with B6 outcome columns. Split to note: B6 itself is deterministic — no multi-run sampling needed — but the CU-extracted service_address feeding it is not, so end-to-end match-rate measurement stays on the multi-run column-append protocol.
  6. All offline, no Azure dependencies, following the test_field_policy_gates.py pattern. Harness passes before any threshold is considered validated.

12 · Risks and open items

R1 — Reference data quality is the ceiling. Unit numbers confirmed clean; street-name consistency across 50K records is not. Step 0 of implementation: run address_norm.py over the full Dynamics export and report canonicalization failures and intra-master duplicates before tuning thresholds. If two master records canonicalize identically, no matcher can distinguish them. The §10 exercise is the proof of value: four real strings surfaced five amendments no synthetic fixture would have produced.
  • O1 — Dataverse field mapping and conventions (sharpened by §10): (a) which columns hold address line 1/2, unit, city, postal; (b) does the master store civic ranges for commercial buildings (drives A2 range expansion); (c) does it use HSE-style designators on houses with secondary/laneway units (drives A3 soft-match semantics). Conventions (b) and (c) decide the outcome for half of the real sample.
  • O2 — Threshold calibration: 92 / 80 / 5 / span-30 are engineering priors. Validate against a labeled sample (~100 real invoices with known correct property) via the scorecard before go-live; adjust with a policy version bump.
  • O3 — Snapshot cadence: nightly assumed. If properties onboard mid-day with same-day invoices expected, supplement the timer with an on-demand resync trigger (HTTP endpoint, function-key protected).
