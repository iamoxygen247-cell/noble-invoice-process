Invoice Diagnostics & Troubleshooting — Runbook

Noble Invoice Processor · how to diagnose a past invoice run (wrong value, wrong routing, or a stuck row)

tool: scripts\diag.py evidence: invoice-diagnostics blobs + ledger stamps replay: offline, no CU cost design record: invoice-diagnostics-design.html

What exists per run. Every invoice processed by the Function leaves: a ledger row in InvoiceExtractProcessLog (routing decision, policy stamps, AnalyzerId, CuDurationMs, failure stamps, blob paths) and two blobs in the invoice-diagnostics container — <rk>/<ts>-raw.json (the full raw Content Understanding result: every field twin, value, confidence) and <rk>/<ts>-decision.json (exactly what Power Automate received). Blobs are auto-deleted after 90 days by a lifecycle rule.
Deployment boundary. The sidecar records runs processed after the diagnostics code was deployed (func azure functionapp publish func-invoiceprocess-westus --build remote). Older runs have only the basic ledger stamps — see §8.

1Point your shell at the right storage

Deployed runs (real Azure storage)

# the connection string wins if set, and would silently hit Azurite instead
Remove-Item Env:AZURE_TABLES_CONNECTION_STRING -ErrorAction SilentlyContinue
$env:AZURE_STORAGE_ACCOUNT = "stinvoicedevwestus"
$env:PYTHONPATH = "$env:LOCALAPPDATA\az-truststore"   # TLS-inspection fix for venv Python
az login                                              # DefaultAzureCredential uses your CLI login

Your user account needs data-plane roles on the storage account: Storage Blob Data Reader and Storage Table Data Reader. Owner/Contributor alone does not grant data access — a 403 AuthorizationPermissionMismatch means these roles are missing (assign them via Access Control (IAM) exactly like the Function's role; RBAC takes a few minutes to propagate).

Local runs (Azurite)

$env:AZURE_TABLES_CONNECTION_STRING = "UseDevelopmentStorage=true"   # Azurite must be running

2Find the sourceId

diag.py is keyed on the SharePoint item UniqueId GUID. If you only know the filename: Azure portal → storage account → Storage browser → Tables → InvoiceExtractProcessLog → filter FileName eq <name>.pdf — the RowKey is the sourceId. The Power Automate run history also shows it in the Function's response body.

3Pull everything for the run

.\.venv\Scripts\python.exe scripts\diag.py --source-id <guid>

Prints the ledger row and downloads both artifacts to out\diag\<guid>\. Read the row top-down:

ColumnWhat it tells you
Status / RoutingDecision Did the run finish, and which path — HAPPY_PATH_CANDIDATE, REVIEW_B4_CRITICAL_FIELD, REJECT_B2_OTHER_CATEGORY, REVIEW_NO_CHILD_EXTRACTION.
FailedStage / LastError For a row at Failed (or stuck at Received on pre-2026-07 rows): the verbatim CU failure (timeout, auth, throttle, ContentSourceNotAccessible…). For infrastructure failures the diagnosis usually ends here.
AnalyzerId / PolicyVersion Which child analyzer produced the fields, and which field-policy code version stamped the decision. Compare PolicyVersion to the current field_policy.POLICY_VERSION before trusting a replay comparison (§6).
CuDurationMs CU analyze wall-clock. Values creeping toward the 100 s timeout signal service degradation.
DefaultedFields / IsHandwritten Which date fields were defaulted by policy; the advisory handwriting label.
RawResultBlob / DecisionBlob Blob paths of the two artifacts. Empty strings = the best-effort sidecar write failed for that run (reason in the Function's App Insights logs) or the run predates the sidecar.

4Read the decision JSON (<ts>-decision.json)

This is exactly what the flow received. For the field that came out wrong, check:

  • fields.<name> — the final value and confidence.
  • resolutions.<name> — which twin won (extract, generate, or agreement) and whether it passed the B4 gate. A correct value losing to a wrong twin is a field_policy.py resolution problem, not a CU problem.
  • reviewReasons / advisoryFlags — why it routed to review, if it did.
  • writeValues — what the flow would have written to Dynamics.

5Read the raw CU result (<ts>-raw.json)

Find the field in the child content's fields block and look at both twins (<name>_extract, <name>_generate) with their confidences. This is what CU actually returned on that run.

A re-run is not evidence. CU output is not deterministic — classification labels and confidences flap run-to-run on borderline documents (see the worked example in docs/ai/troubleshooting.md). Only the stored raw result shows what happened at the time.

6Split the fault domain with an offline replay

.\.venv\Scripts\python.exe scripts\diag.py --replay out\diag\<guid>\<ts>-raw.json --file-name <original>.pdf

Runs gates.evaluate on the stored raw response — no CU call, free, deterministic. --file-name matters only for the municipal invoice-number filename fallback; --field-threshold 0.8 tests threshold sensitivity.

ObservationFault domainNext step
Replay matches the stored decision, and the raw twin values are wrong CU analyzer misread the document Prompt work — §7
Replay matches, raw values are right, final decision is wrong Twin resolution / gate / policy logic Fix gates.py / field_policy.py, then re-run the same --replay as the regression check — the stored raw JSON is your test fixture.
Replay differs from the stored decision Gate/policy code changed since that run Compare the row's PolicyVersion with the current field_policy.POLICY_VERSION; check git history between the two.

7If CU misread the document (prompt work)

  1. Get the original PDF from SharePoint (SharePointUrl / FileName on the row).
  2. Iterate the field description on a scratch analyzer so the production analyzer stays untouched (analyzer ids cannot contain -): 
    .\.venv\Scripts\python.exe scripts\create_analyzer.py --analyzer-id <scratchid>
  3. Judge every candidate on 3+ replicate analyze calls, never one — labels flap near the decision boundary.
  4. Before concluding a fix "doesn't work", GET the live analyzer definition and confirm the JSON edit was actually provisioned.
  5. When proven, provision the real analyzer (create_analyzer.py with no override) and re-run the affected document via scripts\test.py.

8Runs that predate the sidecar (or blobs already purged)

Only the decision stamps exist. The single option is a fresh live run — treat its output as indicative, not forensic (§5 warning applies): 

.\.venv\Scripts\python.exe scripts\test.py --file ".\path\to\the.pdf"
Do not pass --source-id <original-guid> casually. Re-posting the same sourceId re-processes the item and overwrites the historical ledger row's decision. By default test.py generates a fresh GUID and leaves the original row untouched.

9Quick reference — common symptoms

SymptomMeaning / action
Row at Failed, FailedStage=cu_analyze CU call failed and the claim was released; LastError has the reason. The very next request for the sourceId re-claims and re-processes. A row lingering at Failed means the flow's retries exhausted — the flow run is visibly Failed; resubmit it after fixing the cause.
Row stuck at Received, FailedStage=cu_analyze Pre-2026-07 failure semantics (or the release lost its etag race). The row is re-claimed automatically on the next request once older than the A1 lease (default 600 s).
Row stuck at Received, no failure stamps Run crashed before any stamp (hard crash / host kill), the release write itself failed (see Function logs), or a run is genuinely in flight right now. If it stays past the A1 lease, the next request re-claims it — the flow retry policy (fixed, 4 × PT4M) exists precisely so its first retry after the failure lands beyond the lease (retries stop at the first success, and the 200 PROCESSING_IN_PROGRESS no-op counts as one).
RawResultBlob / DecisionBlob empty on an Extracted row The best-effort blob write failed (RBAC missing, container/network issue) or the run predates the sidecar. Check App Insights for the "Diagnostics blob write failed" warning.
diag.py fails with AuthorizationPermissionMismatch (403) Your user lacks Storage Blob/Table Data Reader roles on the account (§1).
diag.py fails with CERTIFICATE_VERIFY_FAILED TLS-inspection proxy: set $env:PYTHONPATH = "$env:LOCALAPPDATA\az-truststore" first (see docs/ai/troubleshooting.md).
diag.py shows the Azurite row when you expected the Azure one (or vice versa) AZURE_TABLES_CONNECTION_STRING takes precedence over AZURE_STORAGE_ACCOUNT — set exactly one (§1).
