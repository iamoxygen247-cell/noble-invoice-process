The four numbered arrows are the four trust boundaries. Each is secured by a different mechanism — that is normal in Azure.

2The four trust boundaries (security)

Each arrow answers: who is allowed to make this call, and how do they prove it? Boundaries 1–2 are Power Automate's security. Boundaries 3–4 are the Function's security and are already configured.

#HopMechanismWho/what holds the secret
1SharePoint → Power Automate A Power Automate connection (OAuth on behalf of an identity). The trigger registers a webhook, so SharePoint pushes the event. The signed-in account's permission on the library is the boundary.
2Power Automate → Function chosen Custom connector + the Azure function key stored in the connection. The function key (encrypted in the connection, never in run history).
3Function → Content Understanding Key via Key Vault reference (validated default), or managed identity. Already wired. AZURE_CU_KEY as a Key Vault reference, or the Function's managed identity.
4Function → Ledger (Table Storage) The Function's user-assigned managed identity. Already wired. No secret — RBAC role on the storage account.

Boundary 1 — SharePoint → Power Automate

Power Automate does not "have access to SharePoint" in the abstract. When you add the trigger you create a connection that signs in as some account; that account's permissions on the invoice library are the boundary. Use a dedicated service account (e.g. svc-invoiceflow@<tenant>) granted read on only the invoice library — not your personal account, which couples the flow to your password/MFA and runs with all your permissions.

Boundary 2 — Power Automate → Function custom connector + key

The endpoint is auth_level=FUNCTION, so every caller must present a function key. The custom connector defines the Function's API once (host, the /api/process-invoice path, request/response shape) and keeps the key in the connection — encrypted at rest and never shown in the flow's run history. The key is the secret to protect; treat it like a password.

Premium licensing. The custom connector (and, later, the Dataverse connector) are premium Power Automate connectors. Confirmed available — the flow's owner needs a premium per-user or per-flow license. (You confirmed this is in place.)
Production upgrade (deferred, Phase 5). Replace the key with Easy Auth (Entra) + auth_level=ANONYMOUS and let the flow authenticate with a managed identity / federated credential — secretless. Get the key path working first.

Boundary 3 — Function → Content Understanding already wired

Lives inside the Function. App setting AZURE_CU_KEY = @Microsoft.KeyVault(SecretUri=https://kv-invoice-process-dev.vault.azure.net/secrets/cu-key/) (the validated default), or leave it blank to use the Function's managed identity with Cognitive Services User on invoice-processing-dev-resource. Power Automate never sees this.

Boundary 4 — Function → Ledger (Table Storage) already wired

The user-assigned identity id-invoice-processing-dev holds Storage Table Data Contributor on stinvoicedevwestus; AZURE_CLIENT_ID tells the Function which identity to use. The Function writes Received then Extracted. Power Automate never sees this.

3The flow, action by action

This is the core flow (Phases 0–3). The branch in step 6 only routes for now; the Dataverse/review outputs are Phase 4.

#ActionDetail
1Trigger: "When a file is created (properties only)" (SharePoint) Point at the invoice <site> + <library> (+ optional folder). "Properties only" gives metadata without downloading on the trigger.
2Get file content (SharePoint) File Identifier = the trigger's file identifier. Returns the PDF bytes.
3Compose — contentBase64 Expression base64(body('Get_file_content')). The file-content object's $content is already base64 in some shapes; we confirm the exact form on the first run (the one fiddly spot).
4Call the Function (custom connector action process-invoice) Body: sourceId = file UniqueId (GUID), contentBase64 = step 3, fileName = trigger file name, sourceFileUrl = item link. The key is in the connection, not the body.
5Read the response Pull routingDecision, alreadyProcessed, writeValues, status.
6Switch on routingDecision alreadyProcessed == true → Terminate (Succeeded).
HAPPY_PATH_CANDIDATE → (Phase 4) Dataverse write.
any REVIEW_* / REJECT_* → (Phase 4) review-queue item.
For Phase 3, each branch just logs / Compose so we can confirm routing.
The SharePoint UniqueId. The Function keys everything off the item's UniqueId (a GUID). In the "properties only" trigger this is the item's {Identifier} / Unique Id column; we confirm the exact dynamic-content field on the first build and add a "Get file properties" action only if needed.
Synchronous timeout. Power Automate connector actions have a ~120 s synchronous limit. CU + a Flex Consumption cold start should be well under that for small invoice PDFs. If we ever hit a timeout, the fix is the async 202 + Location polling pattern noted in functionapp/README.md — not a flow redesign.

5Build order (each phase has a verification gate)

Phase 0 — Confirm the Function is callable at all

Before any Power Automate work, POST a sample invoice to the deployed Function with the key. Verify: HTTP 200 + a routingDecision, and a row appears in InvoiceExtractProcessLog. This isolates "is the Function healthy" from "is the flow wired right."

Phase 1 — Custom connector (Boundary 2)

  1. Power Automate → More → Custom connectors → New custom connector → "Create from blank."
  2. General: Host = <HOST>; Base URL = /api.
  3. Security: API key; parameter name x-functions-key; location Header.
  4. Definition: a POST action process-invoice; request body = the JSON shape (sourceId, contentBase64, fileName, sourceFileUrl); response = the decision JSON.
  5. Create a connection and paste the function key as the API key.

Verify: the connector's built-in Test returns 200 for a tiny payload.

Phase 2 — Minimal flow (Boundaries 1 + 2)

Trigger → Get file content → base64 Compose → call the connector. No branching yet. Verify: drop a PDF in SharePoint → the flow runs → 200 → a ledger row reaches Extracted.

Phase 3 — Branching end of first agreement

Add the Switch on routingDecision + the alreadyProcessed Terminate. Each branch just Composes/logs for now. Verify: a happy-path PDF and a review-triggering PDF each take the right branch; re-dropping the same file shows alreadyProcessed:true (Gate A1).

Deferred to a second pass (Phase 4–5). Phase 4: Dataverse "Add a new row" on the happy path (mapping writeValues), the SharePoint review-queue item on review/reject, and the terminal ledger Written update after a Dataverse 201. Phase 5: retry policy, failure notifications, run-history hygiene, and the move to managed-identity / Easy Auth on Boundary 2.
Recommended order: Phase 0 (Function healthy) → Phase 1 (connector tests 200) → Phase 2 (PDF drop → ledger Extracted) → Phase 3 (decision routes correctly, A1 no-op proven). Stop and review, then build the Phase 4 outputs.
