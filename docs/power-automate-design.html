Power Automate Orchestrator — Design & Build Plan

Noble Invoice Processor · SharePoint file event → cloud flow → decision-engine Function

trigger: SharePoint file-created flow→function: custom connector + key scope: core slice (Phases 0–3) steps: click-by-click, validated

Decisions locked in. Flow → Function a Power Automate custom connector holding the function key in its connection (not the HTTP action; managed identity is a later upgrade). Scope build the core slice first — SharePoint trigger → call the Function → the Function writes the ledger → branch on the decision. Dataverse write + review-queue item are a second pass. Licensing premium Power Automate license and environment are ready.
What is already built and is NOT touched by Power Automate. The Function is a single synchronous endpoint POST /api/process-invoice (auth_level=FUNCTION). It calls Content Understanding and writes the ledger rows (Received, then Extracted + decision) using its own managed identity. Gate A1 already makes a double-fired trigger a no-op, so the flow needs no dedup logic. Power Automate's only job is: catch the SharePoint event, hand the file bytes to the Function, and act on the decision it returns.

Placeholders used throughout: <HOST> (Function default host name, e.g. func-invoiceprocess-westus.azurewebsites.net), <KEY> (function key), <site> / <library> (SharePoint target), <environment> (Power Platform environment).

The four numbered arrows are the four trust boundaries. Each is secured by a different mechanism — that is normal in Azure.

2The four trust boundaries (security)

Each arrow answers: who is allowed to make this call, and how do they prove it? Boundaries 1–2 are Power Automate's security. Boundaries 3–4 are the Function's security and are already configured.

#HopMechanismWho/what holds the secret
1SharePoint → Power Automate A Power Automate connection (OAuth on behalf of an identity). The trigger registers a webhook, so SharePoint pushes the event. The signed-in account's permission on the library is the boundary.
2Power Automate → Function chosen Custom connector + the Azure function key stored in the connection. The function key (encrypted in the connection, never in run history).
3Function → Content Understanding Key via Key Vault reference (validated default), or managed identity. Already wired. AZURE_CU_KEY as a Key Vault reference, or the Function's managed identity.
4Function → Ledger (Table Storage) The Function's user-assigned managed identity. Already wired. No secret — RBAC role on the storage account.

Boundary 1 — SharePoint → Power Automate

Power Automate does not "have access to SharePoint" in the abstract. When you add the trigger you create a connection that signs in as some account; that account's permissions on the invoice library are the boundary. Use a dedicated service account (e.g. svc-invoiceflow@<tenant>) granted read on only the invoice library — not your personal account, which couples the flow to your password/MFA and runs with all your permissions.

Boundary 2 — Power Automate → Function custom connector + key

The endpoint is auth_level=FUNCTION, so every caller must present a function key. The custom connector defines the Function's API once (host, the /api/process-invoice path, request/response shape) and keeps the key in the connection — encrypted at rest and never shown in the flow's run history. The key is the secret to protect; treat it like a password.

Premium licensing. The custom connector (and, later, the Dataverse connector) are premium Power Automate connectors. The flow's owner needs a premium per-user or per-flow license. (You confirmed this is in place.)
Production upgrade (deferred, Phase 5). Replace the key with Easy Auth (Entra) + auth_level=ANONYMOUS and let the flow authenticate with a managed identity / federated credential — secretless. Get the key path working first. The custom connector survives this change; only its security type changes from API key to OAuth.

Boundary 3 — Function → Content Understanding already wired

Lives inside the Function. App setting AZURE_CU_KEY = @Microsoft.KeyVault(SecretUri=https://kv-invoice-process-dev.vault.azure.net/secrets/cu-key/) (the validated default), or leave it blank to use the Function's managed identity with Cognitive Services User on invoice-processing-dev-resource. Power Automate never sees this.

Boundary 4 — Function → Ledger (Table Storage) already wired

The user-assigned identity id-invoice-processing-dev holds Storage Table Data Contributor on stinvoicedevwestus; AZURE_CLIENT_ID tells the Function which identity to use. The Function writes Received then Extracted. Power Automate never sees this.

3The flow at a glance

The full click-by-click build is Section 5. This table is the map; the branch in step 6 only routes for now — the Dataverse/review outputs are Phase 4.

#ActionDetail
1Trigger: "When a file is created (properties only)" (SharePoint) Point at the invoice <site> + <library> (+ optional folder). "Properties only" gives metadata without downloading on the trigger.
2Get file content (SharePoint) File Identifier = the trigger's Identifier. Returns the PDF bytes.
3Compose — contentBase64 Expression body('Get_file_content')?['$content'] — the Get-file-content output already carries the base64 in its $content property (validated). Do not wrap it in base64() as well, or you double-encode.
4Call the Function (custom connector action Process invoice) Body: sourceId = the trigger's Identifier (stable per-file key), contentBase64 = step 3, fileName = file name, sourceFileUrl = item link. The key is in the connection, not the body.
5Read the response Pull routingDecision, alreadyProcessed, writeValues, status.
6Condition + Switch alreadyProcessed == true → Terminate (Succeeded).
else Switch on routingDecision: HAPPY_PATH_CANDIDATE → (Phase 4) Dataverse; any REVIEW_* / REJECT_* → (Phase 4) review item.
For Phase 3 each branch is just a Compose placeholder to confirm routing.
Why the trigger Identifier, not the GUID "UniqueId". The "properties only" trigger exposes the File Identifier (a string), not SharePoint's GUID UniqueId (validated). The Function uses sourceId as an opaque, stable idempotency key — it sanitises whatever string you pass and uses it as the ledger row key — so the Identifier works directly with no extra action. We feed the same Identifier to both "Get file content" and sourceId so it stays consistent across re-fires (which is what Gate A1 needs). Fetching the literal GUID would require an extra "Send an HTTP request to SharePoint" call and is only worth it if you specifically want the ledger key to equal SharePoint's GUID.
Synchronous timeout. Power Automate connector actions have a ~120 s synchronous limit. CU + a Flex Consumption cold start should be well under that for small invoice PDFs. If we ever hit a timeout, the fix is the async 202 + Location polling pattern noted in functionapp/README.md — not a flow redesign.

5Build — click by click

Four phases, each ending in a concrete verification you can see. Do them in order — each gate isolates the next phase's failures.

Phase 0 — Prove the Function answers (no Power Automate yet)

This removes the Function from suspicion before you build anything in Power Automate.

  1. Open PowerShell and cd to the repo, then read <HOST> and <KEY>: 
    cd "C:\Users\georg\dev\Noble Homes\Invoice Extractor\noble-invoice-process"
az functionapp show -g rg-content-understanding-dev -n func-invoiceprocess-westus --query "defaultHostName" -o tsv
az functionapp keys list -g rg-content-understanding-dev -n func-invoiceprocess-westus --query "functionKeys.default" -o tsv
  2. POST a real sample invoice to the deployed Function: 
    cd scripts
python verify_fn.py --base-url "https://<HOST>" --key "<KEY>" --file "..\samples\trade1.pdf"
    Add --insecure if a corporate proxy intercepts TLS.
Verify: output shows HTTP 200 and a line like --> routingDecision: HAPPY_PATH_CANDIDATE, with no ledgerWriteError.
If it isn't 200, fix it here first: 401 = wrong key · 404 = wrong host/path · 502 = CU or its role assignment · 500 = storage or its role assignment. Do not start the flow until Phase 0 is green — a healthy Function is the foundation for everything after.

Phase 1 — Build the custom connector (Boundary 2)

Done once. It stores the key and defines the Process invoice action your flow will call.

A · Create the connector

  1. Go to make.powerautomate.com. Top-right environment picker → confirm you are in <environment>.
  2. Left nav → … More → Discover all → under Data choose Custom connectors (pin it for next time).
  3. Top-right → + New custom connector → Create from blank. Name it Noble Invoice Function → Continue.

B · General tab

  1. Scheme: HTTPS.
  2. Host: <HOST> — host only, no https:// and no /api.
  3. Base URL: /api.

C · Security tab

  1. Authentication type: API Key.
  2. Parameter label: Function key.
  3. Parameter name: x-functions-key (exact, lowercase — this is the header Azure Functions reads).
  4. Parameter location: Header.

D · Definition tab — add the action

  1. + New action. Summary = Process invoice; Operation ID = process-invoice.
  2. Under Request → Import from sample. Verb = POST; URL = https://<HOST>/api/process-invoice; paste this body, then Import: 
    {
  "sourceId": "sample-id",
  "contentBase64": "JVBERi0xLjQK",
  "fileName": "invoice1.pdf",
  "sourceFileUrl": "https://contoso.sharepoint.com/sites/x/invoice1.pdf"
}
    This generates the request body schema (the four fields).
  3. (Recommended) Under Response → + Add default response → Import from sample, paste a trimmed success body so the outputs are typed for the flow: 
    {
  "routingDecision": "HAPPY_PATH_CANDIDATE",
  "alreadyProcessed": false,
  "status": "Extracted",
  "writeValues": {}
}
  4. Top-right → Create connector.

E · Test tab — prove the key + reachability

  1. + New connection → paste <KEY> → Create connection. Back on Test, refresh and select it.
  2. Send a deliberately empty body {} (clear the test fields) → Test operation.
Verify: you get HTTP 400 with a message like request body must be JSON / sourceId is required. A 400 proves success here — the request reached the Function and the key was accepted. (401 = wrong key; 404 = wrong host/Base URL.)
Use an empty body for this test on purpose. The Function rejects a missing sourceId before it writes anything, so the connector test leaves no junk ledger row. (A body with a real sourceId would claim a ledger row.)

Phase 2 — Build the minimal flow (Boundaries 1 + 2)

A · Trigger

  1. make.powerautomate.com → + Create → Automated cloud flow. Name Noble Invoice – Process.
  2. Search the trigger When a file is created (properties only) (SharePoint) → select → Create. If prompted, sign the SharePoint connection in as the service account.
  3. On the trigger: Site Address = <site>; Library Name = <library>. Leave Folder blank for the whole library.

B · Get file content

  1. + New step → search SharePoint → Get file content.
  2. Site Address = same <site>. Click File Identifier → Dynamic content → pick Identifier (from the trigger).

C · base64 (Compose)

  1. + New step → Compose (Data Operation). Rename it (… menu → Rename) to contentBase64.
  2. Click Inputs → Expression tab → paste body('Get_file_content')?['$content'] → OK.
    If you renamed "Get file content", match the name in the expression (spaces become underscores).

D · Call the connector

  1. + New step → Custom tab → Noble Invoice Function → Process invoice. Pick the connection that holds the key.
  2. Fill the body:
    • sourceId = Identifier (trigger) — the stable idempotency key
    • contentBase64 = Outputs of the contentBase64 Compose
    • fileName = File name with extension (trigger)
    • sourceFileUrl = Link to item (trigger)
  3. Save.
Verify: upload a PDF into <library> → open My flows → Noble Invoice → run history → the Process invoice action shows 200 and a routingDecision. Then confirm the ledger row reached Extracted: 
az storage entity query --account-name stinvoicedevwestus --table-name InvoiceExtractProcessLog `
  --auth-mode login --num-results 5 `
  --query "items[].{rk:RowKey, status:Status, decision:RoutingDecision}" -o table
If the action returns 502 after a real upload: Phase 0 already proved CU works, so suspect the contentBase64 expression. The Function 502s if it can't base64-decode the body. Re-check the Compose expression is exactly body('Get_file_content')?['$content'].

Phase 3 — Add branching end of first agreement

A · Already-processed short-circuit

  1. After Process invoice → + New step → Control → Condition.
  2. Left value (Expression): body('Process_invoice')?['alreadyProcessed'] · operator is equal to · right value (Expression): true.
  3. If yes → Add an action → Control → Terminate → Status Succeeded. (A re-fired trigger ends cleanly as a no-op.)

B · Switch on the decision (inside "If no")

  1. In the If no branch → Add an action → Control → Switch.
  2. On (Expression): body('Process_invoice')?['routingDecision'].
  3. Case 1 equals HAPPY_PATH_CANDIDATE → add a Compose "HAPPY — would write Dataverse (Phase 4)".
  4. Case 2 equals REVIEW_B4_CRITICAL_FIELD → Compose "REVIEW — would write review item (Phase 4)". (Optionally add cases REJECT_B2_OTHER_CATEGORY, REVIEW_NO_CHILD_EXTRACTION.)
  5. Default → Compose "REVIEW/REJECT — would write review item (Phase 4)".
  6. Save.
Verify three things:
  • Upload a clean invoice → the HAPPY case Compose ran.
  • Upload one that should review (e.g. a non-8-digit PO/job number) → the review case / Default ran.
  • Open the first clean run in history → Resubmit it → the alreadyProcessed Condition goes yes → Terminate. (Resubmit reuses the same Identifier, so Gate A1 returns alreadyProcessed:true — this is the idempotency proof.)
Deferred to a second pass (Phase 4–5). Phase 4: replace the Compose placeholders — Dataverse "Add a new row" on the happy path (mapping writeValues), a SharePoint review-queue item on review/reject, and the terminal ledger Written + DynamicsRecordId update after Dataverse returns 201. Phase 5: retry policy, failure notifications, run-history hygiene, and the move to managed-identity / Easy Auth on Boundary 2.
Recommended order: Phase 0 (Function answers 200) → Phase 1 (connector test returns 400 = reached + authorized) → Phase 2 (PDF drop → ledger Extracted) → Phase 3 (decision routes correctly, A1 no-op proven on resubmit). Stop and review, then build the Phase 4 outputs.
