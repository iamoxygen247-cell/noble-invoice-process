Python 3.13 → 3.14 Migration

Noble Invoice Processor · local venvs + the Flex Consumption Function App

target: Python 3.14.7 plan: Flex Consumption FC1 cutover: in place evidence verified: 2026-08-20

⛔ This migration takes production down for one deploy. The outage window opens at step 4a (the runtime flip is saved) and closes at step 4b (the remote-build redeploy completes). Steps 1–3 are entirely local and steps 5–7 are documentation — neither touches the app. Full detail in § The outage window.
Who runs what (2026-08-20). Steps 1–4 are run by hand by the operator — they rebuild the venvs, pre-flight the wheels, and cut the app over. Steps 5–7 are documentation and were done separately. This page is the source of truth for the migration; any planning notes elsewhere are superseded by it.
Naming, so nobody relaxes. The app lives in rg-content-understanding-dev, but it is the production instance — the 2026-08-19 watermark records the analyzer and function app verified live at HEAD, and the separate prod environment in docs/provision-azure-environment.html is still unprovisioned. The “dev” in the resource-group name is historical, not a safety net.

Why this changed

The repo carried a standing rule against this migration, repeated in four places (CLAUDE.local.md, docs/provision-azure-environment.html, docs/deploy-to-azure.html, docs/project-playbook.md §7.4):

“Stay on Python 3.13: 3.14 has no remote-build support on Flex Consumption, and deploys use func … publish --build remote.”

That rule was true when written and is now false. Evidence gathered 2026-08-20:

ClaimStatus todaySource
3.14 unsupported on Flex GA, EOL Oct 2030 ARM az functionapp list-flexconsumption-runtimes returns python 3.14, skuCode FC1, endOfLifeDate 2030-10-31; Learn Supported languages lists Python 3.14 as GA
Remote build broken for 3.14 on Flex Fixed 2026-06-23, deployed to all regions Azure/azure-functions-python-worker#1801, closed as completed: “The fix has been deployed to all regions, so remote build for Python 3.14 is now fully supported”

Outcome: one Python version (3.14.7) locally and in the cloud, a runtime supported to Oct 2030 rather than Oct 2029, and the end of the recurring Local python version '3.14.x' is different from '3.13' warning noise.

Decisions taken (user, 2026-08-20). Migrate local and Azure; cut over in place accepting a short outage; leave requirements.txt constraints unpinned.

  • Steps 5–7 are documentation. They happen after the app is healthy.
  • The window is exactly 4a → 4b. Nothing else here causes downtime.
  • Confirm it is closed with check 7 (no ModuleNotFoundError at worker init) and definitively with check 8 (smoke test returns 200).
Stage the 4b publish command in a second terminal before you flip. The window is your reaction time plus the deploy — do not flip and then go hunting for a terminal. And note the duration is dominated by this machine's ARM flakiness, not by Azure: the documented measurement is 1 successful func publish in 8 attempts on 2026-08-18 through the TLS inspector. Budget for retries; 4b is written as a retry loop.

A rollback re-opens a second, identical window — Flex Consumption has no deployment slots, so there is nothing to swap.

Compatibility & impact

Verified compatible

  • Source compiles clean on 3.14. All 16 project .py files compiled under the real 3.14.7 interpreter with 0 syntax errors and 0 warnings.
  • Conservative stdlib surface. Only argparse, base64, csv, datetime, hashlib, html, json, logging, mimetypes, os, pathlib, re, ssl, subprocess, sys, time, urllib, uuid, zoneinfo, typing. No datetime.utcnow(), no distutils, no multiprocessing (so 3.14's Linux forkserver default is irrelevant).
  • Every file already uses from __future__ import annotations, so PEP 649/749 lazy annotations in 3.14 cannot change behaviour here.
  • All dependencies ship cp314 wheels. cryptography 50.0.0 ships abi3 wheels (one wheel covers 3.9+) plus explicit cp314; cffi 2.1.1 ships cp314-manylinux_2_17_x86_64 and cp314-win_amd64. azure-functions 2.2.0 declares requires_python >=3.13 and a Python :: 3.14 classifier.
  • host.json bundle [4.*, 5.0.0) is already the version a language-version change requires — no change.

No functional drift expected in the decision engine

The three places an interpreter swap could leak into output were checked directly:

  • Money — round(float(total) - float(gst), 2), abs(a-b) < 0.005: IEEE-754 doubles and banker's rounding are unchanged.
  • Dates — strptime / strftime / fromisoformat: no 3.14 semantic change, and ZoneInfo("America/Vancouver") resolves from the tzdata wheel, not the interpreter.
  • Ordering — sets are membership/dedup only, output order follows source lists, and the single sorted() is stable.

Blast radius

The app is a single HTTP-triggered function (@app.route(route="process-invoice", …)), called synchronously by Power Automate. No queue or timer trigger, so nothing accumulates a backlog or poisons a queue.

Why the flip breaks the running app: with --build remote packages are built server-side against the app's configured runtime, so the order is forced — flip first, then rebuild. In between, cffi (and multidict/propcache/ yarl) ship version-tagged .so files (…cpython-313-x86_64-linux-gnu.so) that 3.14 will not import. (cryptography is abi3 and would survive — cffi alone is enough.)

The failure mode is clean. Because the worker dies at import, gate A1 never runs: no ledger claim is taken, no partial ledger row is written, no diagnostics blob is half-written. Invoices posted during the window simply fail and can be re-posted — function_app.py re-claims and fully re-processes a repeat sourceId by design.

Azure settings: nothing to change

The live app has exactly 13 settings — A1_LEASE_SECONDS, APPLICATIONINSIGHTS_CONNECTION_STRING, AZURE_CLIENT_ID, AZURE_CU_ANALYZER_ID, AZURE_CU_API_VERSION, AZURE_CU_ENDPOINT, AZURE_CU_GENERAL_ANALYZER_ID, AZURE_CU_TIMEOUT_SECONDS, AZURE_STORAGE_ACCOUNT, AZURE_TABLES_TABLE, and the three AzureWebJobsStorage__* keys — none of them Python-version dependent.

Three settings are absent and must stay absent. FUNCTIONS_WORKER_RUNTIME (invalid on Flex — the runtime lives in functionAppConfig), FUNCTIONS_EXTENSION_VERSION (deprecated on Flex), and any PYTHON_* setting — PYTHON_ENABLE_INIT_INDEXING is unnecessary because init indexing is on by default from 3.13 up. Check after the deploy that nothing injected them.

Out of scope

  • No analyzers/*.json edits ⇒ no prod analyzer push.
  • No corpus or sidecar changes. This is neither an extraction bug fix with a reproduction PDF nor a requirement change. scripts/regress.py caches by (analyzer_hash, pdf_hash, replicate) — the Python version is not in the cache key, so the cache stays valid and the corpus run makes zero CU calls.
  • No dependency version changes — requirements.txt keeps its >= constraints.
  • func-noble-stratadocument (rg-noble-strata) is a different project's Flex app in the same subscription. Do not touch it.

1Rebuild the local venvs on 3.14 local only

3.14.7 is already installed at %LOCALAPPDATA%\Python\pythoncore-3.14-64\python.exe and is already the py -0p default. A venv hard-codes its base interpreter in pyvenv.cfg and cannot be upgraded in place — recreate both. 

$PY314 = "$env:LOCALAPPDATA\Python\pythoncore-3.14-64\python.exe"
& $PY314 --version          # expect: Python 3.14.7

# Root venv - pytest, scripts/, and the pre-commit hook all use this one
Remove-Item -Recurse -Force .\.venv
& $PY314 -m venv .\.venv
.\.venv\Scripts\python.exe -m pip install --upgrade pip
.\.venv\Scripts\python.exe -m pip install -r .\functionapp\requirements.txt
.\.venv\Scripts\python.exe -m pip install pytest truststore

# functionapp venv - used only by a local `func start`
Remove-Item -Recurse -Force .\functionapp\.venv
& $PY314 -m venv .\functionapp\.venv
.\functionapp\.venv\Scripts\python.exe -m pip install -r .\functionapp\requirements.txt
.\functionapp\.venv\Scripts\python.exe -m pip install truststore
pytest and truststore are deliberately not in requirements.txt. truststore is this machine's TLS-inspection workaround and is unwanted on the Azure Linux host. Install them explicitly or the pre-commit hook and scripts/regress.py break.
Verify: --version reports 3.14.7 for both venvs, and -m pip check is clean for both.

3Pre-flight the Linux cp314 wheel set local only

Your laptop is Windows; the Function App is Linux. Flex Consumption is Linux-only, and --build remote builds the packages on Azure. So the artifacts that decide whether 4b succeeds are manylinux cp314 wheels — a different set of files from the win_amd64 wheels step 1 installs. Step 1 passing proves nothing about step 4b.

This is the step that de-risks the outage. If any dependency lacks a manylinux cp314 wheel, pip on the build host falls back to compiling from source and blows the documented 60-second remote-build timeout — failing inside the outage window, with production already down. Resolve the whole transitive set locally first. pip download only fetches wheels into a temp folder; it modifies neither venv. 

.\.venv\Scripts\python.exe -m pip download -r .\functionapp\requirements.txt `
    --only-binary=:all: `
    --implementation cp --python-version 314 `
    --platform manylinux_2_28_x86_64 `
    --platform manylinux_2_17_x86_64 `
    --platform manylinux2014_x86_64 `
    --dest "$env:TEMP\wheelcheck-linux-cp314"
All three --platform tags are required. pip download --help: “Use this option multiple times to specify multiple platforms supported by the target interpreter.” Packages tag wheels inconsistently — cffi 2.1.1 ships cp314-cp314-manylinux2014_x86_64.manylinux_2_17_x86_64.whl with no manylinux_2_28 tag, so a single --platform manylinux_2_28_x86_64 would reject it and report a false failure. Do not pass --abi: omitting it lets pip accept abi3 wheels such as cryptography's.
Pass = every dependency resolved to a wheel, printed as Saved …, and no .tar.gz source distributions in the destination folder.
Run 2026-08-20: PASS. 25 wheels, 0 sdists, exit code 0. Seven compiled wheels, all manylinux: cffi, charset_normalizer, cryptography (cp311-abi3), markupsafe, multidict, propcache and — the one dependency PyPI's truncated file list could not confirm — yarl-1.24.5-cp314-cp314-manylinux2014_x86_64…whl. The remote build in 4b will find a wheel for everything.
⚠ Keep the --dest path short (Windows MAX_PATH). These manylinux filenames carry three platform tags and run to ~90 characters, so a deep destination blows the 260-character limit and pip dies mid-download with FileNotFoundError: [Errno 2] No such file or directory on a wheel it already resolved. That is not a missing wheel — resolution had already succeeded. Hit for real on 2026-08-20 with a nested temp folder; $env:TEMP\wheelcheck-linux-cp314 is short enough.
If it fails it names the offending package. Do not proceed to step 4. A source-only dependency would break the remote build with production already down. Pin that one package to a version that ships a cp314 wheel, then re-run.
Core Tools stays at 4.12.0 — do not upgrade it as part of this migration. An earlier draft of this page told you to run winget upgrade Microsoft.Azure.FunctionsCoreTools to reach 4.13.0. That was wrong twice over: winget only offers 4.12.1 (the warning fix is in 4.13.0, GitHub-only), and swapping build tooling immediately before a production deploy trades a proven-good binary for a cosmetic gain. 4.12.0 is known to deploy successfully to 3.14 Flex apps. Upgrade later from the GitHub release, if ever.

4Cut the Azure app over production

Confirm az works first — az account show proves nothing, it only reads the local token cache:

$az = "$env:LOCALAPPDATA\az-truststore\shim\az.cmd"
& $az account get-access-token --query expiresOn -o tsv    # must succeed

4a Flip the runtime version — the outage starts here

On Flex the version lives at properties.functionAppConfig.runtime.version, not in siteConfig.

⚠ az functionapp config set --linux-fx-version / --python-version do not work on Flex. They write siteConfig, which Flex ignores — the exact trap reported in Azure/Azure-Functions#2638. Learn's generic Update language versions Linux/CLI tab will send you there. Don't go.

Portal — lowest risk on this machine. It is documented as supported for Flex on Linux and avoids the flaky Python-based az transport entirely (a browser handles the inspection CA fine): Function App → Settings → Configuration → General settings → Python Version → 3.14 → Save → Continue.

CLI alternative — the body file avoids PowerShell/JSON quoting problems:

$SUB = "<subscription id>"          # recorded in CLAUDE.local.md
$RG  = "rg-content-understanding-dev"
$APP = "func-invoiceprocess-westus"
$URL = "https://management.azure.com/subscriptions/$SUB/resourceGroups/$RG" +
       "/providers/Microsoft.Web/sites/$APP?api-version=2024-04-01"

'{"properties":{"functionAppConfig":{"runtime":{"name":"python","version":"3.14"}}}}' |
    Set-Content -Encoding utf8 .\out\runtime-314.json

& $az rest --method patch --url $URL --body "@out/runtime-314.json"
Prefer this targeted PATCH over az resource update --set, which does a GET-then-PUT of the whole site object.

Verify the flip — check the runtime and that nothing else was collateral damage:

& $az rest --method get --url $URL --query "properties.functionAppConfig" -o json

Assert both:

  • runtime → {"name":"python","version":"3.14"}
  • deployment.storage.authentication.type → still UserAssignedIdentity, and deployment.storage.value still points at the function-deployments container.
⚠ Why the second assertion exists. A nested PATCH that sends functionAppConfig.runtime alone can, if the provider shallow-replaces functionAppConfig, null out deployment.storage — the keyless wiring rebuilt on 2026-07-14. That would break the deploy in 4b while production is already down. The portal path has no such failure mode, which is the main reason it is recommended over the CLI. If deployment did come back null, restore it before running 4b.

4b Redeploy immediately — the outage ends here

cd functionapp
$deployed = $false
for ($i = 1; $i -le 8; $i++) {
    "--- publish attempt $i ---"
    func azure functionapp publish $APP --build remote | Tee-Object -Variable log
    if (($log -join "`n") -match 'The deployment was successful') { $deployed = $true; break }
    "attempt $i did not land - retrying"
}
if (-not $deployed) {
    Write-Warning "8 attempts with no success line - check the portal before publishing again"
}
⚠ Do not use if ($LASTEXITCODE -eq 0) { break } here. func exits non-zero even when the deploy succeeds (the trailing SSL error described below), so an exit-code loop never breaks — it would re-publish up to 8 times and hold the outage open for every one of them. Match on the success string instead. Note also that 2>&1 is deliberately absent: this shell is PowerShell 5.1 Desktop, which wraps native stderr in ErrorRecords and would corrupt the match.
Three things that look like failures and are not.
  • Can't find app with name "func-invoiceprocess-westus" — an ARM 10054 reset. It means retry, not wrong app name.
  • A trailing SSL error after The deployment was successful! — func fetches invoke URLs last, through the inspector. The deploy already landed. Read the log, not the exit code.
  • On Core Tools 4.12.0 only: Remote build for Python 3.14 is not yet supported for Flex — stale and non-blocking; the build succeeds. Gone in 4.13.0.
The window is closed once the worker re-initializes on the new package. Confirm with checks 7 and 8 below.

Rollback

Flex Consumption has no deployment slots, so there is no swap. Rollback is the same two steps in reverse and opens a second outage window of the same shape:

  1. PATCH properties.functionAppConfig.runtime.version back to "3.13" (or portal → Python Version → 3.13 → Save). Window opens.
  2. func azure functionapp publish $APP --build remote from the same commit — the remote build re-resolves against 3.13 and restores a working package. Window closes.

Locally, recreate the two venvs with pythoncore-3.13-64\python.exe — 3.13 is still installed alongside 3.14 (py -0p lists both), so nothing needs reinstalling.

No analyzer, app setting, RBAC assignment, or ledger schema changes — so there is nothing else to undo.
