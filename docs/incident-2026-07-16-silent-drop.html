Noble Invoice Processor · incident report & fix

2026-07-16 — a CU timeout became a green flow run that wrote nothing

File 260601_0002.PDF · dev environment (func-invoiceprocess-westus) · root cause verified against the live ledger row · fix shipped in the same repo change as this report

1 · What was observed

The Power Automate run showed the Process_invoice action succeeding with HTTP 200, but the body was a skip:

{
  "alreadyProcessed": true,
  "skippedCU": true,
  "status": "Received",
  "routingDecision": "PROCESSING_IN_PROGRESS",
  "reviewReasons": ["A1: another invocation is currently processing this SharePoint item"]
}

The immediate question was: why 200 when this looks like an error? Short answer: the 200 is by design — gate A1 skips are contractually a no-op, not an error. The flow branches on the body (alreadyProcessed == true → Terminate Succeeded), never on the HTTP status, and the custom connector declares only a single default response. The real defect is the chain of events that produced this response — and what the flow did with it.

(The x-ms-apihub-cached-response: true header in the run output is a Power Platform APIHub-layer artifact and was a red herring — the connector is POST-only and the body was a genuine, freshly generated function response.)

2 · Root cause — verified timeline

The ledger row (InvoiceExtractProcessLog on stinvoicedevwestus) recorded the whole story:

Status          = Received
RoutingDecision = ""
FailedStage     = cu_analyze
LastError       = "Content Understanding analyze did not complete within 120s"
IngestedUtc     = 2026-07-16T16:25:17Z
LastUpdatedUtc  = 2026-07-16T16:27:17Z   (exactly 120 s later)
Time (UTC)Event
16:25:17 Invocation #1 claims the A1 row (Status=Received) and starts the CU analyze.
16:27:17 CU hits its 120 s cap. The failure handler stamps FailedStage/LastError but leaves Status=Received (old design: “resume after the lease”), and returns 502. The connector's own hard ~120 s budget expired at almost the same moment, so the flow saw a timeout.
16:27:19 Power Automate's default retry policy (retries timeouts and 5xx automatically) re-calls the function. The retry finds a Received row only 2 s old — well inside the 600 s A1 lease (A1_LEASE_SECONDS) — and gets the 200 PROCESSING_IN_PROGRESS skip above.
— The flow's alreadyProcessed == true Condition fires → Terminate (Succeeded). Green run. No Dataverse write. And because the SharePoint trigger fires only once per file, nothing ever comes back for this invoice.
Three compounding defects.
  1. On a graceful CU failure the function knew the run was over but kept the A1 claim, locking out the automatic retry for up to 600 s.
  2. The CU cap (120 s) did not undercut the connector budget (~120 s), so the structured 502 never reached the flow — it saw an opaque timeout instead.
  3. The retry's PROCESSING_IN_PROGRESS no-op terminated the run Succeeded, making the drop invisible.

3 · The fix (code, shipped with this report)

  • functionapp/ledger.py — claim() and reclaim() now return the written row's etag (None when they lose the race) instead of a boolean.
  • functionapp/function_app.py — on a CU failure the function releases its claim: an etag-conditioned merge sets Status=Failed (plus FailedStage/LastError). A Failed row is immediately re-claimable, so the flow's automatic retry re-processes within seconds instead of hitting PROCESSING_IN_PROGRESS. The condition uses this invocation's own claim etag — never a re-read — so a delayed release can never clobber a newer invocation's claim. If the etag loses, nothing is stamped and the old lease fallback applies. The 502 body now reports status: "Failed" (or "Received" when the release lost).
  • functionapp/cu_client.py — default CU cap lowered 120 s → 100 s so the 502 + release always lands before the connector budget expires.
  • Tests — D3 contract updated (Status=Failed, immediate-retry re-process), plus a new race-regression test proving a foreign etag bump makes the release a no-op.
Follow-up hardening (same day): the decision path after CU (gate evaluation through the response build) got the same etag-conditioned Failed release (FailedStage=decision, HTTP 500), and A1_LEASE_SECONDS was lowered to 300 s on dev (code default stays 600 s). Residual case (mitigated by the retry policy below): a hard crash (host killed, out-of-memory — no release written) still leaves Received for the full lease. The retry policy below is sized so the first retry after such a failure lands beyond the lease and re-claims the stale row.

4 · Power Automate — exact steps

A. Set the retry policy on the Process_invoice action (required)

  1. Go to make.powerautomate.com → My flows → open the invoice flow → Edit.
  2. Select the Process_invoice action (the custom connector call).
  3. Open its Settings (new designer: the Settings tab in the right-hand pane; classic designer: ⋮ → Settings).
  4. Under Networking → Retry policy, change Default to:
    • Type: Fixed Interval
    • Count: 4
    • Interval: PT4M (4 minutes)
  5. Save the flow.

Why these values: retries stop at the first success, and a 200 PROCESSING_IN_PROGRESS counts as a success (the flow terminates as a no-op) — so the rule is that the first retry after a claim-holding failure must land beyond the A1 lease: interval > lease − 120 s (a hard crash fails at the ~120 s connector timeout). With the lease at 300 s (set 2026-07-16; code default 600 s), PT4M puts the first retry at ≈360 s — past the lease with ~60 s margin — so a hard-crashed run's stale claim is re-claimed and re-processed on that first retry. A shorter interval like PT2M would land at ≈240 s, inside the lease, get the 200 no-op, and end the chain — a permanent silent drop. Graceful CU failures don't depend on any of this: the released (Failed) row is re-claimable immediately.

B. Nothing else changes in the flow or connector

  • The custom connector definition stays as-is (POST, single default response).
  • The alreadyProcessed == true → Terminate (Succeeded) Condition and the routingDecision Switch stay as-is — the response contract is unchanged.

C. After the code deploy — recover the dropped invoice

  1. My flows → the invoice flow → 28-day run history.
  2. Find the 2026-07-16 ~16:27 UTC run for 260601_0002.PDF (it shows Succeeded despite writing nothing).
  3. Open it → Resubmit. The ledger row is long past the lease, so the resubmit re-claims and fully re-processes. (Alternative: re-upload the file to the SharePoint drop folder.)
  4. Verify the resubmitted run took the routingDecision Switch branch (not Terminate), and/or that the ledger row reached Status=Extracted.

D. Optional (recommended)

  • Add a flow-failure notification (Teams/email on run failure). After this fix, exhausted retries surface as a genuinely Failed run instead of a silent green no-op — so a notification now actually means something.

5 · Live remediation (dev function app)

  1. Set the app setting AZURE_CU_TIMEOUT_SECONDS=100 on func-invoiceprocess-westus (resource group rg-content-understanding-dev) — immediate mitigation, independent of the deploy.
  2. Deploy the function: func azure functionapp publish func-invoiceprocess-westus --build remote.
  3. Apply the retry policy (Section 4A) and resubmit the dropped run (Section 4C).
