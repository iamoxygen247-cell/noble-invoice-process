Azure Naming Convention & Remediation Plan

Noble Invoice Processor · one standard, the current-state audit, and how (and how far) to correct dev

workload token: invoice pattern: <type>-invoice-<env>-<region> style: Microsoft CAF audit date: 2026-07-05 (live, via az)

The one fact that shapes everything here: Azure resources cannot be renamed. The only renameable thing in the current estate is a subscription display name. Every other "rename" is really create-new → migrate → delete-old. That is why this plan (a) applies the convention perfectly to the new production environment (which starts from scratch), and (b) treats correcting dev as a phased, mostly optional cleanup.

1The standard

Pattern

<type>-<workload>-<env>-<region>[-<instance>]

  type      CAF resource-type abbreviation (table below)
  workload  invoice            (fixed — one canonical token, never "invoiceprocess",
                                "invoice-processing", "content-understanding", …)
  env       dev | prod
  region    westus             (spelled out, matching current usage)
  instance  -01, -02 …         only when a second instance of the same type exists

  Storage accounts (no hyphens allowed, ≤ 24 chars, lowercase alphanumeric):
  st<workload>[<qualifier>]<env><region>      e.g. stinvoiceprodwestus, stinvoicefuncprodwestus

3Recommendation: which environment becomes production?

Question asked: is it easier to keep the current environment as production and provision the new one as dev?

Recommendation: no — keep the current environment as dev and provision production fresh (this is what docs/provision-azure-environment.html does). Reasons:
  • Names are permanent. Promoting the current environment would put production on resources permanently named …-dev / invoice-processing-dev-resource, inside a subscription that (pre-rename) says dev-…. The naming problem this document exists to fix would be locked into production forever.
  • The switchover cost is the same either way. Production Power Automate needs its own environment-scoped connector, connection and flow regardless of which Azure environment it points at — so "keeping" the current environment saves no orchestrator work.
  • A fresh prod validates the runbook. The current environment was built by hand; building prod from the provisioning doc proves the whole environment is reproducible — which is exactly what you want to be true of production.
  • Clean ledger. Prod starts without months of dev/test rows in InvoiceExtractProcessLog.
The honest trade-off: the new prod is an unproven deployment on day one, while the current environment is battle-tested. Mitigation: the runbook's smoke tests (400-validation, real invoice, A1 resubmit, ledger check, App Insights live metrics) exercise every trust boundary before any real invoice flows — and dev remains available for side-by-side comparison of the same PDF.

4Correcting dev — three phases

Phases 0–1 are cheap and safe; do them now. Phase 2 is the full rename-by-recreation — genuinely optional, because after prod exists the wrong names live only in dev where they cost nothing but aesthetics.

Phase 0 — free, immediate (no resources touched)

  1. Adopt the standard for everything new — starting with the entire prod build.
  2. Rename the subscription display names (the one true rename Azure allows): Portal → Subscriptions → select → Rename: dev-Document Intelligence → dev-Invoice Processing, and name the new one prod-Invoice Processing.
    After renaming, update the two places in this repo that reference the old display name: docs/deploy-to-azure.html (step 0) and functionapp/README.md — plus CLAUDE.local.md (gitignored).

Phase 1 — decommission the two unused resources (low risk)

Both were part of earlier iterations and are dead weight (and S0 Cognitive Services accounts can bill on use — zero use, but zero value too). Verify, then delete.

# --- ai-content-understanding-dev-01 (unused CognitiveServices account) ---
# 1. Confirm nothing references it: no role assignments scoped to it...
$OLD_AI_ID = az cognitiveservices account show -g rg-content-understanding-dev `
  -n ai-content-understanding-dev-01 --query id -o tsv
az role assignment list --scope $OLD_AI_ID -o table                      # expect: empty

# ...and the Function's settings point at invoice-processing-dev-resource, not this:
az functionapp config appsettings list -g rg-content-understanding-dev -n func-invoiceprocess-westus `
  --query "[?name=='AZURE_CU_ENDPOINT'].value" -o tsv

# 2. Delete (CognitiveServices soft-deletes; purge makes the name reusable)
az cognitiveservices account delete -g rg-content-understanding-dev -n ai-content-understanding-dev-01
az cognitiveservices account purge  -g rg-content-understanding-dev -n ai-content-understanding-dev-01 -l westus

# --- kv-invoice-process-dev (unused Key Vault) ---
# 1. Confirm the app has no Key Vault references (verified 2026-07-05: none)...
az functionapp config appsettings list -g rg-content-understanding-dev -n func-invoiceprocess-westus `
  --query "[?contains(value, 'KeyVault')].name" -o json                  # expect: []

# ...and inventory any secrets before losing them:
az keyvault secret list --vault-name kv-invoice-process-dev --query "[].name" -o tsv

# 2. Delete (Key Vault soft-deletes for 90 days by default — recoverable window)
az keyvault delete -n kv-invoice-process-dev -g rg-content-understanding-dev
Before deleting: both verification commands must come back empty, and give it a once-over in the portal (Metrics → total calls, last 30 days) if in doubt. Deletion is the one irreversible step in this document — soft-delete windows aside.

Phase 2 — optional: rebuild dev under conforming names

Do this only after prod is live and stable. It is literally the provisioning runbook re-run with $ENVTOKEN = "dev", plus a small migration and cleanup. Skipping it forever is acceptable — document the legacy names and move on.

  1. Run docs/provision-azure-environment.html with $ENVTOKEN = "dev" — but skip the data-storage creation: stinvoicedevwestus already conforms. Instead, move it into the new resource group (a move preserves the name, the table, and every row — no data migration): 
    $ST_ID = az storage account show -g rg-content-understanding-dev -n stinvoicedevwestus --query id -o tsv
az resource move --destination-group rg-invoice-dev-westus --ids $ST_ID
    Moves break role assignments. A moved resource gets a new resource ID, and RBAC scoped to the old ID does not follow. Re-run the two Storage Table Data Contributor assignments (new UAMI + your user) against the moved account — the runbook's step 5 covers it.
  2. Update the code/config touchpoints (verified by repo-wide scan, 2026-07-05 — tests and scripts/*.py are clean, everything is env-var driven):
    FileWhat to change
    functionapp/cu_client.py Resolved 2026-07-05: the hardcoded dev endpoint default was removed; AZURE_CU_ENDPOINT is now required and the code fails fast with a clear error when it is missing. Deployable Python carries zero resource names — nothing to change here in Phase 2.
    functionapp/local.settings.json.template AZURE_CU_ENDPOINT and AZURE_STORAGE_ACCOUNT values.
    functionapp/local.settings.json (gitignored, per machine) Same two values.

  4. Verify — the runbook's smoke tests (step 10) against the new dev, plus one PDF through the dev flow; confirm ledger rows land in the moved stinvoicedevwestus.
  5. Delete the old shells once everything is green:

az resource list -g rg-content-understanding-dev -o table    # eyeball what's left FIRST
az group delete -n rg-content-understanding-dev

What never changes in any phase: data-plane names (InvoiceExtractProcessLog, invoicerouter, generalinvoice) are part of the application contract and stay identical in every environment — only control-plane resource names carry env/region tokens.
Summary. Standard: <type>-invoice-<env>-westus (storage: stinvoice[func]<env>westus). Prod is born conforming via the provisioning runbook. Dev: rename the subscription and delete the two unused resources now; the full rebuild is optional and fully scripted whenever it becomes worth an afternoon.
