Invoice Number Filename Fallback + Review-Reasons Summary — Design Review

Noble Homes Invoice Extractor · noble-invoice-process · 2026-07-03 · Prepared for review before implementation
Status: awaiting sign-off. No code has been changed. This document covers two new requirements and one confirmed existing behavior. On approval, implementation proceeds in the order in §7; the offline pytest suite gates every step. No analyzer change and no Power Automate change is required.

1 · The requirements

RequirementBehavior
R1 — filename fallback Municipal bills often carry no printed invoice number. invoice_number is critical for the municipal bucket, so today every such bill routes to REVIEW_B4_CRITICAL_FIELD. New rule: when the invoice number is truly empty on a municipal bill, default it to the SharePoint filename (without extension) and let the bill proceed.
R2 — review summary When a bill fails the critical-field gate (B4), reviewReasons must carry one combined, human-readable message naming every failing field:
1 field → vendor_name needs attention
2 fields → vendor_name and po_or_job_number need attention
3+ fields → vendor_name, po_or_job_number and gst_amount need attention
Confirmed — agreement rule No change needed. When both the extract and generate twins are below the confidence threshold but their values match, the field already passes (source "agreement", extract's literal value written). Proven by an existing test: extract "INV-2201" @ 0.50 + generate "inv 2201" @ 0.60 → passes, writes "INV-2201". The filename fallback never competes with it, because the fallback fires only when both twins are empty.

2 · R1 options considered

OptionAssessmentVerdict
A — Function-side, reuse the existing fileName field The filename already reaches the function: fileName is an existing optional request field, the Power Automate flow already sends the SharePoint filename, and both test scripts (local_test.py, verify_fn.py) already send the real PDF filename. No contract change, no caller breaks, no dummy test value needed. Routing, the ledger audit trail (DefaultedFields), and the offline unit tests all stay consistent. There is a proven in-function pattern to copy: the PO rescue (fill a failed critical field from another deterministic source, mark its source, add an advisory). CHOSEN
B — New required parameter default_invoice_number (original proposal) Works, but duplicates fileName (in production both would carry the same SharePoint filename), and making it required breaks every existing caller until updated: the deployed Power Automate flow, both test scripts, and the hardening tests. Internal testing would need the "INTERNAL INVOICE #" dummy value. All of that buys nothing over option A. rejected
C — Handle it in Power Automate The flow could substitute the filename when writeValues.invoice_number is empty — but the function has already routed the bill to REVIEW_B4_CRITICAL_FIELD before the flow sees the result. The bill would still land in human review unless the flow also overrode the routing decision, which moves field policy out of field_policy.py/gates.py where this project deliberately centralizes it. PA expressions are also unversioned and untestable by the offline suite, and the ledger's DefaultedFields audit would not record the substitution. rejected
D — Analyzer prompt change Not viable: Content Understanding only sees the document bytes. The filename is not in the document, so no prompt can produce it. not viable
Bottom line: the new-parameter proposal is superseded because the data it would carry is already in the request. Option A is a small, surgical change entirely inside the decision engine.

3 · Confirmed design decisions

R1 — filename fallback

  • Trigger — only when truly empty: fires only when both invoice_number_extract and invoice_number_generate produced nothing. A present-but-low-confidence value still routes to review — the filename never overwrites a real candidate a human could confirm.
  • Value — filename without extension: 2026-water-bill.pdf → 2026-water-bill. Punctuation and casing kept as-is.
  • Scope — municipal only: fires only when invoice_number is in the bucket's critical set (i.e. the municipal bucket), mirroring the PO-rescue pattern. Commercial bills are unchanged (the field is informational there).
  • Missing filename — graceful no-op: if fileName is absent or blank (e.g. the ad-hoc url transport), behavior is exactly today's (review). No error, no new required field.
  • Fully audited: the response marks it three ways — resolutions.invoice_number.source = "filename", defaultedFields gains "invoice_number" (persisted to the ledger's existing DefaultedFields column), and an advisory flag records the substituted value. Confidence is reported as 1.0, same rationale as the PO rescue: the value is deterministic, not model output.

R2 — review-reasons summary

  • Replace, not append: on a B4 failure, reviewReasons contains exactly one message — the combined summary. The current per-field diagnostics (confidence values, which twin failed, format hints, the multi-PO-candidate note) move to advisoryFlags, so the result JSON keeps full debugging detail.
  • Uniform wording: needs attention for every failure cause — absent, empty, low confidence, or format violation. (E.g. a vendor_name present at 0.65 confidence reads vendor_name needs attention.)
  • Field naming: twin fields appear by their final name (invoice_number, never invoice_number_extract/invoice_number_generate), listed in critical-set order.
  • Grammar: 1 field → X needs attention; 2 → X and Y need attention; 3+ → X, Y and Z need attention.
  • Scope — B4 only: REJECT_B2_OTHER_CATEGORY, REVIEW_NO_CHILD_EXTRACTION, and gate-A1 short-circuit messages keep their current wording (they are not field failures).

6 · Why no other part of the system changes

  • Request contract Untouched. fileName stays optional; existing callers keep working. The Power Automate flow needs no change — it already sends fileName.
  • Test scripts scripts/local_test.py and scripts/verify_fn.py need zero edits — they already send the real PDF filename, and their scorecards already print invoice_number.source and join reviewReasons generically. The internal-test fallback value is simply the sample PDF's stem (e.g. invoice1); no "INTERNAL INVOICE #" dummy is needed.
  • Ledger Untouched — DefaultedFields is already persisted on every Extracted write.
  • Analyzer Untouched — no prompt or schema change, no re-provisioning.
