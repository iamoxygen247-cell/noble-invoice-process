Noble Invoice Pipeline

Workspace Hardening Review

2026-07-10 · full-workspace audit: functionapp/ code, scripts/, tracked configuration, untracked local artifacts, docs/ provisioning runbooks, and the complete git history (all refs, origin included). All credential values in this report are redacted to a short prefix.

Executive summary

The tracked repository is in good shape: no secrets exist in any tracked file at HEAD, the single HTTP endpoint requires a function key, table keys are sanitized against injection, input is validated before any state change, secrets are read from environment only with a managed-identity fallback, and a prior hardening pass (F1–F5/H1) is regression-tested in tests/test_function_app_hardening.py. The provisioning design is keyless-by-default with least-privilege RBAC.

The remaining gaps concentrate in four areas, in priority order:

  1. Git history: a Content Understanding API key (and two now-expired blob SAS URLs) live in the majority of the repo's commit history, which has been pushed to GitHub (private repo). Rotation is probably done but unconfirmed; the history was never scrubbed. — HG-01, HG-02
  2. Local disk: a live CU key sits in plaintext in functionapp/local.settings.json, and a pre-approved az command echoes it to the terminal; real invoice PII sits in samples/ and out/. — HG-03, HG-08
  3. Azure platform flags: the provisioning runbook creates storage and the Function App without several hardening switches (--https-only, shared-key/public-blob-access disable, network rules). — HG-06
  4. Application code: the ad-hoc url transport is unvalidated (SSRF-shaped), raw exception text is returned to callers, dependencies are unpinned, and there is no request payload size cap. — HG-04, HG-05, HG-07, HG-09

Findings

HG-01 High Content Understanding API key committed across most of git history, pushed to GitHub

Where: history of scripts/step24_test.py, scripts/step21_test.py, scripts/step24_test_old.py, scripts/model_deployment_info.py (e.g. step24_test.py:57 at commit 3127eab) · remote: github.com/iamoxygen247-cell/noble-invoice-process (private)

An 84-character AI Services key (9n1Mwhx3…, redacted) for invoice-processing-dev-resource.services.ai.azure.com was hardcoded as API_KEY = "…" in early prototype scripts. It was removed from HEAD (commits ba6c735 "replaced key with identity" and 1414f19 "cleanup old files"), but it remains retrievable from the majority of historical commits via git log -p / git show, and that history has been pushed to the GitHub remote.

Mitigating evidence found:

  • The repo is private (unauthenticated GitHub API returns 404).
  • The key currently in functionapp/local.settings.json (2E8z…) is a different value than the leaked one, and docs/ai/troubleshooting.md:132-134 describes the old hardcoded key as "stale/rotated" — so rotation very likely already happened, but nothing confirms it, and AI Services resources have two keys (the leaked one could be the un-rotated twin).
  • README.md:119-125 acknowledges the past hardcoding but only says to regenerate "if it was ever committed" — it was.

Fix:

  1. Confirm the leaked key is dead — regenerate both keys (idempotent and instant; then update local.settings.json / the Key Vault secret if key auth is still used anywhere): 
    az cognitiveservices account keys regenerate -g rg-content-understanding-dev `
  -n invoice-processing-dev-resource --key-name key1
az cognitiveservices account keys regenerate -g rg-content-understanding-dev `
  -n invoice-processing-dev-resource --key-name key2
  2. Scrub history with git-filter-repo (also removes the HG-02 SAS URLs). Create a fresh clone first; filter-repo refuses to run on a dirty working copy: 
    # replacements.txt — one line per secret (full literal values, taken from history)
#   <the full leaked key>==>REDACTED
#   <each full sig=… SAS token>==>REDACTED
.\.venv\Scripts\python.exe -m pip install git-filter-repo
git filter-repo --replace-text replacements.txt
git push --force origin main
    Afterwards every collaborator must re-clone (old clones still hold the secret), and any other refs (forks, other branches) must be rewritten or deleted. GitHub may retain unreachable commits in cache/pull-request refs — contact GitHub support to purge if the repo will ever be made public.
  3. Optionally enable GitHub push protection (Settings → Code security) so a future accidental key push is blocked at the boundary; secret scanning for private repos requires Advanced Security, but push protection for common Azure key patterns is worth checking on the current plan.
Do not skip step 1 by relying on the "stale/rotated" note — the confirmation costs one command and closes the only path by which this finding is exploitable today.

HG-03 High Live CU key handling on this machine: plaintext file, echoed by an allowlisted az query, passed as a CLI argument

Where: functionapp/local.settings.json:7 (untracked, gitignored — verified never committed) · .claude/settings.json:5 · scripts/test.py:595

Three related exposure paths for live keys during local development:

  • The current CU key (2E8z…) sits unencrypted in functionapp/local.settings.json. Git hygiene is correct (ignored, never committed — verified with git log --all --diff-filter=A and content search across all refs), so the risk is disk-level: backups, cloud sync, malware, screen sharing.
  • The pre-approved command in .claude/settings.json:5 projects {name, value} for all AZURE_* app settings — running it prints the deployed AZURE_CU_KEY value into the terminal and any session transcript.

    az functionapp config appsettings list -g $RG -n $APP `
  --query "[?contains(name,'AZURE_')].name" -o table
  3. In scripts/test.py, read the function key from an environment variable (e.g. FUNCTION_KEY) with --key kept only as an explicit override, and note the history caveat in its --help text.

HG-04 Medium Unvalidated url transport passed to a server-side fetch (SSRF vector)

Where: functionapp/function_app.py:130-134 → :238 → functionapp/cu_client.py:154-163

The request body's url field is accepted with no scheme/host validation and handed to begin_analyze(inputs=[AnalysisInput(url=url)]), which Azure Content Understanding fetches server-side. The docstrings label it "ad-hoc test only," but nothing gates it — the path is fully reachable in the deployed app by anyone holding the function key. Mitigations already in place: the caller must be authenticated (FUNCTION auth level), and the fetch originates from Azure CU's infrastructure, not the function's own network — so classic instance-metadata SSRF doesn't apply, but it still lets a caller make CU pull arbitrary URLs and can probe endpoints reachable by CU.

Fix: gate the transport off in production and validate what remains. In _decode_content (function_app.py):

ALLOW_URL_TRANSPORT = os.getenv("ALLOW_URL_TRANSPORT", "").lower() == "true"

url = body.get("url")
if isinstance(url, str) and url.strip():
    if not ALLOW_URL_TRANSPORT:
        return None, None, "url transport is disabled; use contentBase64"
    parsed = urllib.parse.urlparse(url)
    if parsed.scheme != "https":
        return None, None, "url must be https"
    return None, url, None

Leave ALLOW_URL_TRANSPORT unset in the deployed app settings (disabled by default); set it true only in local.settings.json when ad-hoc testing with a Blob SAS URL. Optionally add a host allowlist (e.g. *.blob.core.windows.net) if the transport must stay enabled anywhere. Add a regression test alongside the existing transport tests in tests/test_function_app_hardening.py.

HG-05 Medium Raw exception detail returned to the HTTP caller

Where: functionapp/function_app.py:207, :218, :245, :269/282

Ledger and CU failures embed str(exc) in the JSON response ("error": f"ledger A1 write failed: {exc}", ledgerWriteError, etc.). Azure SDK exception messages routinely contain endpoint URLs, storage account names, request IDs, and auth-failure specifics — internal detail disclosed to whoever holds the function key, and recorded into Power Automate run history. Full stack traces already stay server-side (every path calls logging.exception first — good); only the message string leaks.

Fix: return a generic message plus the invocation ID for correlation, keep the detail in App Insights. Example pattern for the A1 handler (repeat for all four sites):

except Exception:
    logging.exception("Ledger A1 / Received write failed")   # detail stays in logs
    return _json(500, {"sourceId": source_id, "partitionKey": pk, "rowKey": rk,
                       "error": "ledger write failed",
                       "invocationId": context.invocation_id})

(Add context: func.Context to the function signature to get the invocation ID.) Note the response contract is consumed by the Power Automate flow — ledgerWriteError becoming generic is fine (the flow keys off status), but re-run the flow's failure branch after the change. Update the assertions in tests/test_function_app_hardening.py that match on error text.

HG-06 Medium Provisioning runbook creates resources without platform hardening flags

Where: docs/provision-azure-environment.html steps 3 and 7 · applies retroactively to the live dev environment (func-invoiceprocess-westus, stinvoicedevwestus)

Verified against the actual az commands in the runbook:

  • az functionapp create (line ~245) is run without --https-only true, and no minTlsVersion is ever set on the app — a plaintext HTTP call carrying the function key is not rejected at the platform.
  • Both az storage account create calls set --min-tls-version TLS1_2 (good) but neither sets --allow-blob-public-access false nor considers --allow-shared-key-access false; the ledger table is created with --auth-mode key even though the design is RBAC/managed-identity.
  • No network restrictions anywhere: no --default-action Deny, no VNet/private endpoints, no --public-network-access settings. Acceptable for a dev prototype; should be an explicit decision for prod (the prod provisioning runbook is derived from this doc).

Fix — retrofit dev now, and add the same flags to the runbook (and the prod runbook derived from it):

# Function App: force HTTPS + TLS floor
az functionapp update -g $RG -n $APP --set properties.httpsOnly=true
az functionapp config set -g $RG -n $APP --min-tls-version 1.2

# Data/ledger storage account: no anonymous blob access, RBAC-only data plane
az storage account update -g $RG -n $ST_DATA --allow-blob-public-access false
az storage account update -g $RG -n $ST_DATA --allow-shared-key-access false
# ...and switch the runbook's table create to RBAC:
az storage table create --account-name $ST_DATA --name $TABLE --auth-mode login
Caveat for the runtime account ($ST_FUNC): the Functions host wires AzureWebJobsStorage and DEPLOYMENT_STORAGE_CONNECTION_STRING as connection strings (the runbook notes this). Do not disable shared-key access on $ST_FUNC until the app is switched to identity-based host storage (Flex Consumption supports managed-identity deployment storage); otherwise the app breaks. Disabling public blob access on $ST_FUNC is safe immediately.

For prod: additionally decide on --default-action Deny + IP rules or private endpoints for $ST_DATA, and record the decision in docs/provision-azure-environment.html either way.

HG-07 Medium Dependencies are unpinned (>= floors, no lockfile)

Where: functionapp/requirements.txt (all six entries)

Every dependency is a floor (azure-functions>=1.20.0, azure-ai-contentunderstanding>=1.1.0, …). Because deploys use func … publish --build remote, Azure resolves whatever is newest at build time — each deploy can silently pick up a different dependency tree, including a breaking or compromised release. This is both a supply-chain and a reproducibility gap.

Fix: pin exact versions from the known-good local environment and keep the floors as comments:

.\.venv\Scripts\python.exe -m pip freeze | Select-String "azure-|tzdata"
# copy the resulting == versions into functionapp/requirements.txt

Refresh deliberately (e.g. monthly) with a test pass, rather than implicitly on every deploy. A hash-locked file (pip-compile --generate-hashes) is the stronger version if you want to add a dev dependency; exact pins alone are a big step up and need no new tooling.

Where: samples/ (real vendor PDFs: BC Hydro, FortisBC, trade invoices, property tax, …) · out/verify_result.json, out/verify_scorecard.html (extracted vendor names, service addresses, invoice/PO numbers, amounts)

But they hold real third-party billing documents and production-shaped extracted data in plaintext, regenerated on every harness run. The Azurite emulator artifacts (__azurite_db_*.json) were checked and are clean — the ledger holds only GUIDs, status, and routing decisions, consistent with ledger.py never persisting extracted field values.

Fix:

  • Exclude the repo folder from any cloud-sync tool (OneDrive/Dropbox) — sync would copy customer PII and the key file off-machine.
  • Never zip/share the workspace root; share git archive output instead (tracked files only).
  • Purge out/ when a verification round is done, and confirm retention of samples/ is acceptable under Noble Homes' data-handling expectations (they are needed for the harness, so this is a policy check, not a deletion demand).

HG-09 Low No size cap before base64 decode (memory-amplification DoS)

Where: functionapp/function_app.py:120-128

contentBase64 is regex-stripped and decoded with no length check; the string, its compacted copy, and the decoded bytes coexist in memory (~2.75× the payload), and an authenticated caller can send up to the platform body limit (≈100 MB). One line closes it — before re.sub: 

MAX_CONTENT_B64_CHARS = 45_000_000   # ≈ 33 MB decoded; invoices are <10 MB

if len(content_b64) > MAX_CONTENT_B64_CHARS:
    return None, None, "contentBase64 exceeds the maximum accepted size"

Add a regression test next to the existing transport-validation tests.

HG-10 Low --insecure TLS bypass in the test harness

Where: scripts/test.py:388 (ssl._create_unverified_context())

Opt-in only, off by default, and exists for this machine's TLS-inspecting proxy — an acceptable harness accommodation, and it never ships (deploy unit is functionapp/ only, where TLS verification is never touched). The residual risk is habit: combining --insecure with a real function key against the deployed endpoint would let an active MITM capture the key. Fix: print a one-line warning when --insecure is used with a non-localhost URL. No code change needed beyond that.

HG-11 Low host.json relies entirely on platform defaults

Where: functionapp/host.json

No functionTimeout, no retry policy, no HTTP concurrency caps — abuse control rests solely on the function key. Since the CU call is already capped at 120 s (cu_client.DEFAULT_ANALYZE_TIMEOUT_SECONDS), an explicit "functionTimeout": "00:05:00" bounds worst-case invocation cost cheaply. Concurrency throttles are optional at this traffic level; note them for prod capacity planning instead.

HG-12 Low Docs disagree on the Function→CU auth model

Where: docs/power-automate-design.html (Key Vault-referenced AZURE_CU_KEY as "validated default") vs docs/provision-azure-environment.html (keyless by design, AZURE_CU_KEY deliberately unset)

Not an exposure, but the ambiguity invites an operator to mint an unnecessary CU key during prod provisioning. The keyless/managed-identity path is the stronger default and is what the provisioning runbook already grants roles for. Fix: update power-automate-design.html to present keyless as the default and the Key Vault key as the fallback, matching the runbook.

HG-13 Info Minor notes (no action required)

  • The initiating begin_analyze_binary/begin_analyze call relies on azure-core's default transport timeouts; only the polling phase has the explicit 120 s cap (cu_client.py:109-120). Azure-core defaults are sane; acceptable.
  • _json serializes with default=str (function_app.py:67) — could stringify an unexpected object repr into a response; payloads are hand-built dicts today.
  • ExpiresAt is written to ledger rows but Azure Table Storage has no native TTL — data retention needs an external cleanup job eventually (ops, not security).
  • local.settings.json.template and several docs disclose dev resource hostnames — identifiers, not secrets; accepted.

Verified What is already solid

Confirmed during this review — future reviews should not re-flag these:

  • No secrets in any tracked file at HEAD, and none of local.settings.json, samples/, Azurite artifacts, or *.key files were ever committed (verified via git log --all --diff-filter=A and content search across all refs). .gitignore / .funcignore coverage is correct.
  • Endpoint auth: single POST route with auth_level=FUNCTION (function_app.py:175); Power Automate stores the key in the connector connection and sends it as the x-functions-key header — never in the URL or run history.
  • Secrets discipline in code: keys/connection strings read from env only; AZURE_CU_ENDPOINT deliberately has no default; DefaultAzureCredential/managed identity is the preferred path (cu_client.py, ledger.py); TLS verification is never disabled in the deployable.
  • Injection surface: table partition/row keys sanitized (ledger.py:37-52); no blob/file paths built from user input; no eval/exec/pickle/subprocess anywhere in the app.
  • Request validation before state change (strict base64, threshold range-check, required sourceId) with the A1 claim only after validation — all regression-tested in tests/test_function_app_hardening.py, along with the CU LRO timeout cap and ledger-truth status reporting.
  • No PII in logs: log lines carry the source GUID and decision only; the Azurite ledger confirmed the design writes no extracted field values.
  • Provisioning design: least-privilege RBAC (one user-assigned identity with exactly Cognitive Services User + Storage Table Data Contributor), storage created with --min-tls-version TLS1_2, explicit Log Analytics/App Insights wiring, restrictive default CORS untouched.
  • Tooling hygiene: .claude/settings.json allowlist is narrow and read-only (aside from HG-03's value projection); tests use stubs and placeholder URLs only; analyzers/*.json contain no secrets or PII.
