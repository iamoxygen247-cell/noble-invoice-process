Provision an Azure Environment — End-to-End

Noble Invoice Processor · resource group → storage → Content Understanding → identity → Function App → analyzers → deploy → Power Automate

target env: prod region: westus runtime: Python 3.13 · Flex Consumption (FC1) auth: keyless (user-assigned identity) naming: see docs/naming-convention.html

What this runbook builds. A complete, standalone environment for the invoice pipeline: resource group, two storage accounts (ledger data + Function runtime), an AI Services (Content Understanding) resource, a user-assigned managed identity with least-privilege RBAC, Log Analytics + Application Insights, a Flex Consumption Function App, the two CU analyzers, the deployed Function code, and the production Power Automate connector/flow. It is written for prod but is fully parameterized — re-run it with the dev name set (see the naming doc) to rebuild dev later.
Run order matters. Steps are dependency-ordered: RBAC (step 5) must exist before the analyzers (step 8) and the smoke test (step 10); the general analyzer must exist before the router (the router's JSON references analyzerId: generalinvoice). Each step ends with a Verify command — do not continue past a failed verify.

Placeholders used throughout: <SUB-ID> (new subscription id), <UAMI-CLIENT-ID> (managed-identity client id, captured in step 5), <HOST> / <KEY> (Function host + key, step 11). Secrets (keys, connection strings) are never written into files in this repo.

1Parameters — set once per PowerShell session

Every later command uses these variables. The names follow the repo convention (<type>-invoice-<env>-<region>, defined in docs/naming-convention.html). Storage accounts drop hyphens (Azure: 3–24 chars, lowercase letters/digits only).

$RG       = "rg-invoice-$ENVTOKEN-$LOC"     # rg-invoice-prod-westus

$ST_FUNC  = "stinvoicefunc$ENVTOKEN$LOC"    # stinvoicefuncprodwestus (Function runtime)

3Storage — data account + runtime account + the ledger table

Two accounts, mirroring dev: the data account holds the InvoiceExtractProcessLog ledger (geo-redundant), the runtime account is the Function App's own storage (locally redundant is fine — it holds only deployment packages and host state).

# Data / ledger account (RAGRS = read-access geo-redundant, parity with dev)
az storage account create -g $RG -n $ST_DATA -l $LOC `
  --sku Standard_RAGRS --kind StorageV2 --min-tls-version TLS1_2 `
  --tags env=$ENVTOKEN workload=invoice

# Function runtime account (LRS)
az storage account create -g $RG -n $ST_FUNC -l $LOC `
  --sku Standard_LRS --kind StorageV2 --min-tls-version TLS1_2 `
  --tags env=$ENVTOKEN workload=invoice

# The ledger table ( --auth-mode key uses your Owner right to read the account key;
# your data-plane RBAC role arrives in step 5 )
az storage table create --account-name $ST_DATA --name $TABLE --auth-mode key
Verify: 
az storage account list -g $RG --query "[].{name:name, sku:sku.name}" -o table
az storage table list --account-name $ST_DATA --auth-mode key --query "[].name" -o tsv   # -> InvoiceExtractProcessLog

4AI Services — the Content Understanding resource

Kind AIServices (the Azure AI Foundry multi-service resource — same kind as dev's invoice-processing-dev-resource). The --custom-domain is required: Entra/managed-identity auth and the services.ai.azure.com endpoint only work with a custom subdomain.

az cognitiveservices account create -g $RG -n $AIF -l $LOC `
  --kind AIServices --sku S0 --custom-domain $AIF --yes `
  --tags env=$ENVTOKEN workload=invoice
Endpoint. The app setting in step 7 uses the Foundry-style endpoint https://$AIF.services.ai.azure.com/ — the same form dev uses. Content Understanding is region-limited; westus is a supported region (it is where dev runs today).
Verify: 
az cognitiveservices account show -g $RG -n $AIF --query "{kind:kind, sku:sku.name, endpoint:properties.endpoint}" -o json

5Managed identity + RBAC (least privilege)

One user-assigned managed identity; it is how the Function reaches CU and the ledger — no keys.

az identity create -g $RG -n $UAMI -l $LOC --tags env=$ENVTOKEN workload=invoice

# Capture its three ids
$UAMI_ID        = az identity show -g $RG -n $UAMI --query id -o tsv
$UAMI_CLIENT_ID = az identity show -g $RG -n $UAMI --query clientId -o tsv
$UAMI_PRINCIPAL = az identity show -g $RG -n $UAMI --query principalId -o tsv

# Scopes
$AIF_ID     = az cognitiveservices account show -g $RG -n $AIF --query id -o tsv
$ST_DATA_ID = az storage account show -g $RG -n $ST_DATA --query id -o tsv

# The identity's two roles (exactly what dev's identity holds)
az role assignment create --assignee-object-id $UAMI_PRINCIPAL --assignee-principal-type ServicePrincipal `
  --role "Cognitive Services User" --scope $AIF_ID
az role assignment create --assignee-object-id $UAMI_PRINCIPAL --assignee-principal-type ServicePrincipal `
  --role "Storage Table Data Contributor" --scope $ST_DATA_ID

# Your own account needs the same two roles — for create_analyzer.py (step 8)
# and the ledger verification query (step 10)
$ME = az ad signed-in-user show --query id -o tsv
az role assignment create --assignee-object-id $ME --assignee-principal-type User `
  --role "Cognitive Services User" --scope $AIF_ID
az role assignment create --assignee-object-id $ME --assignee-principal-type User `
  --role "Storage Table Data Contributor" --scope $ST_DATA_ID
RBAC propagation can take up to ~5 minutes. If step 8 or 10 returns 401/403 right after this step, wait and retry before changing anything.
Verify: 
az role assignment list --assignee $UAMI_PRINCIPAL --all --query "[].{role:roleDefinitionName, scope:scope}" -o table
Expect exactly Cognitive Services User (CU scope) and Storage Table Data Contributor (data-storage scope).

6Monitoring — Log Analytics + Application Insights

Created explicitly with convention names — this avoids the portal's auto-generated DefaultWorkspace-… / app-named component that dev ended up with.

az monitor log-analytics workspace create -g $RG -n $LAW -l $LOC `
  --tags env=$ENVTOKEN workload=invoice
$LAW_ID = az monitor log-analytics workspace show -g $RG -n $LAW --query id -o tsv

az monitor app-insights component create --app $APPI -l $LOC -g $RG `

7Function App — Flex Consumption, Python 3.13

az functionapp create -g $RG -n $APP `
  --flexconsumption-location $LOC `
  --runtime python --runtime-version 3.13 `
  --storage-account $ST_FUNC `
  --app-insights $APPI `
  --tags env=$ENVTOKEN workload=invoice

# Attach the user-assigned identity
az functionapp identity assign -g $RG -n $APP --identities $UAMI_ID
Two platform-managed leftovers. (1) The Flex Consumption plan is auto-created by this command with a generated name — it is exempt from the naming convention (see the naming doc). (2) The CLI wires AzureWebJobsStorage and DEPLOYMENT_STORAGE_CONNECTION_STRING to $ST_FUNC automatically — do not edit them. Stay on Python 3.13: 3.14 has no remote-build support on Flex Consumption and step 9 deploys with --build remote.

8Provision the two CU analyzers

Analyzers are data-plane objects inside the CU resource — a new resource starts empty. Push both definitions from analyzers/. Order matters: the router's JSON references analyzerId: generalinvoice, so create the general analyzer first.

cd "C:\Users\georg\dev\Noble Homes\Invoice Extractor\noble-invoice-process"

# Point the script at the NEW resource (AZURE_CU_ENDPOINT is required — the script
# has no default endpoint and errors out rather than silently targeting another env)
$env:AZURE_CU_ENDPOINT = "https://$AIF.services.ai.azure.com/"

# 1) generalinvoice (default definition file)
.\.venv\Scripts\python.exe scripts\create_analyzer.py

# 2) invoicerouter (references generalinvoice)
.\.venv\Scripts\python.exe scripts\create_analyzer.py `
  --file analyzers\create-router-analyzer.json --analyzer-id invoicerouter
Auth: the script uses your az login (needs the Cognitive Services User role granted in step 5). If local Python hits the machine's TLS-inspection (CERTIFICATE_VERIFY_FAILED), use the key fallback documented in docs/ai/troubleshooting.md: set AZURE_CU_KEY for the session from az cognitiveservices account keys list -g $RG -n $AIF — never write the key to a file.
Verify: each run ends with Done. analyzer_id=generalinvoice… / Done. analyzer_id=invoicerouter….

10Smoke test + ledger check

# Host + function key
$FN_HOST = az functionapp show -g $RG -n $APP --query defaultHostName -o tsv
$FN_KEY  = az functionapp keys list -g $RG -n $APP --query functionKeys.default -o tsv

cd "C:\Users\georg\dev\Noble Homes\Invoice Extractor\noble-invoice-process"

# 1) Validation path (no data written) -> expect HTTP 400
.\.venv\Scripts\python.exe scripts\verify_fn.py --base-url "https://$FN_HOST" --key "$FN_KEY" --bad-payload

# 2) Real invoice -> expect HTTP 200 + routingDecision, writes the FIRST prod ledger row
.\.venv\Scripts\python.exe scripts\verify_fn.py --base-url "https://$FN_HOST" --key "$FN_KEY" --file ".\samples\trade1.pdf"

# 3) Re-post the same source id -> alreadyProcessed:true (gate A1 works in prod)
.\.venv\Scripts\python.exe scripts\verify_fn.py --base-url "https://$FN_HOST" --key "$FN_KEY" `
  --file ".\samples\trade1.pdf" --source-id <SID_FROM_STEP_2>

# Ledger rows landed
az storage entity query --account-name $ST_DATA --table-name $TABLE `
  --auth-mode login --num-results 5 `
  --query "items[].{rk:RowKey, status:Status, decision:RoutingDecision}" -o table

Add --insecure to verify_fn.py calls if the corporate proxy intercepts TLS. Triage: 401 = wrong key · 404 = wrong host/path · 502 = CU or its role assignment · 500 = storage or its role assignment.

Verify: 400 → 200 + routingDecision → alreadyProcessed:true, and the table shows Status=Extracted. The Azure environment is now fully live — what remains is wiring the orchestrator to it.

11Power Automate — production connector, connection, flow

Condensed build with prod values. The full click-by-click walkthrough, designer notes, schema rationale and troubleshooting live in docs/power-automate-design.html — use it side by side; only the values below change.

A · Prerequisites

  • A Power Platform production environment (custom connectors are environment-scoped — the dev connector is not reachable from another environment).
  • Premium Power Automate license for the flow owner (custom connectors are premium).
  • The production SharePoint <site> + <library> where invoices land, and ideally a dedicated service account (svc-invoiceflow@<tenant>) with read on that library only.
  • <HOST> and <KEY> from step 10 ($FN_HOST / $FN_KEY), or from the portal: Function App → Overview → Default domain; key under the process_invoice function → Function keys.

B · Custom connector (once per environment)

  1. make.powerautomate.com → environment picker → the production environment.
  2. Solutions → open/create an unmanaged solution → New custom connector → Create from blank → name Noble Invoice Function (prod).
  3. General: Scheme HTTPS · Host = <HOST> (host only — no https://, no path) · Base URL /api.
  4. Security: Authentication API Key · label Function key · parameter name x-functions-key (exact, lowercase) · location Header → Create connector.
  5. Definition: + New action · Summary Process invoice · Operation ID process-invoice. Request → Import from sample: verb POST, URL https://<HOST>/api/process-invoice, body: 
    {
  "sourceId": "sample-id",
  "contentBase64": "JVBERi0xLjQK",
  "fileName": "invoice1.pdf",
  "sourceFileUrl": "https://contoso.sharepoint.com/sites/x/invoice1.pdf"
}
    Response → + Add default response → Import from sample: 
    {
  "routingDecision": "HAPPY_PATH_CANDIDATE",
  "alreadyProcessed": false,
  "status": "Extracted",
  "ledgerWriteError": "",
  "writeValues": {}
}
    → Update connector.
  6. Test: + New connection → paste <KEY> → create. On the Test tab select the connection, leave the body empty → Test operation.
Verify: HTTP 400 (sourceId is required) — the request reached prod and the key was accepted, and the deliberately empty body means no junk ledger row was written. 401 = wrong key · 404 = wrong host/Base URL.

C · Cloud flow

  1. + Create → Automated cloud flow, name Noble Invoice – Process (prod), trigger "When a file is created (properties only)" (SharePoint) — sign the connection in as the service account. Site = production <site>, Library = <library>.
  2. Get file content (SharePoint) — File Identifier = the trigger's Identifier.
  3. Compose, renamed contentBase64 — expression body('Get_file_content')?['$content'] (do not wrap in base64() — that double-encodes).
  4. Process invoice (the prod connector action): sourceId = trigger Identifier · contentBase64 = the Compose output · fileName = File name with extension · sourceFileUrl = Link to item.
  5. Condition: body('Process_invoice')?['alreadyProcessed'] equals true → Terminate (Succeeded).
  6. False branch → Switch on body('Process_invoice')?['routingDecision']: cases HAPPY_PATH_CANDIDATE / REVIEW_B4_CRITICAL_FIELD (+ optionally REJECT_B2_OTHER_CATEGORY, REVIEW_NO_CHILD_EXTRACTION) and a Default — with the downstream actions your dev flow settled on (Dataverse write / review item; Compose placeholders until then). Also honor status: "Received" + ledgerWriteError as a failure → review/alert, never a Dynamics write.
  7. Save.
Verify (end-to-end): drop a real invoice PDF into the production library → flow run shows 200 with a routingDecision → the ledger query from step 10 shows the new row at Status=Extracted → Resubmit the run → the Condition goes true → Terminate (idempotency proof, gate A1).
Keep dev and prod fully parallel but separate: separate Power Platform environment, separate connector, separate connection (holding the prod key), separate flow, separate SharePoint library. Nothing in the prod flow may reference func-invoiceprocess-westus (dev).

12Post-provision checklist

  • ☐ All resources present: 
    az resource list -g $RG --query "[].{name:name, type:type}" -o table
    Expect: 2 storage accounts, 1 AIServices account, 1 identity, 1 workspace, 1 App Insights, 1 plan (auto-named), 1 function app.
  • ☐ RBAC audit: the UAMI holds exactly two roles (step 5 verify) — nothing at subscription scope.
  • ☐ Keyless confirmed: AZURE_CU_KEY and AZURE_TABLES_CONNECTION_STRING absent from app settings.
  • ☐ Function key hygiene: the prod key exists only inside the Power Automate connection. Never in this repo, run history, or a tracked file. Rotate it in the portal if it ever leaks — then update the connection.
  • ☐ Budget alert (recommended): Portal → the new subscription → Cost Management → Budgets → + Add — Flex Consumption + S0 are pay-per-use, so an early-warning budget is cheap insurance.
  • ☐ Telemetry flowing: Portal → appi-invoice-prod-westus → Live metrics while re-running a step-10 smoke test.
  • ☐ Update CLAUDE.local.md (gitignored) with the prod subscription/app pointers for future sessions.
Recommended order (recap): subscription + providers → parameters → RG → storage + table → CU resource → identity + RBAC → monitoring → Function App + settings → analyzers (generalinvoice then invoicerouter) → pytest + func publish → smoke tests + ledger check → connector (400 test) → flow (drop a PDF, resubmit for A1) → checklist.
