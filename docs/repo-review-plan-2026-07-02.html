Part 2

Findings across the repo

Ordered by severity. Each has a concrete failure scenario and a proposed fix; nothing is applied yet.

Critical

S1 · Live Azure key committed and pushed to GitHub

scripts/model_deployment_info.py:6 hardcodes a Content Understanding API key. The file is tracked at HEAD and the key pattern appears in 20+ commits of history on origin (github.com/iamoxygen247-cell/noble-invoice-process). Commit ba6c735 (“replaced key with identity”) shows earlier scripts also carried keys, so history is contaminated beyond this one file. This directly contradicts the repo’s own CLAUDE.md secrets rule and the README security section. I could not confirm repo visibility from this machine (TLS interception blocks the GitHub API) — treat the key as compromised either way.

Anyone with repo access (or the public, if the repo is public) can call the CU resource on your subscription — quota burn, data exposure, cost.

(a) Regenerate both keys on the CU resource in the Azure portal — this is the only step that actually revokes access; (b) update the gitignored local.settings.json and the deployed Function app setting with the new key; (c) delete the file; (d) optionally purge history — see Decision 1.

High

F1 · A malformed request locks out its invoice for 10 minutes

In functionapp/function_app.py, the check that the body carries contentBase64 or url happens after gate A1 claims the ledger row (claim at line 144, transport check at line 162–168). The 400 response leaves the row at Received with no decision.

The Power Automate flow sends a request with a missing/misnamed content field → 400. The flow fixes the payload and retries → A1 sees an in-flight row inside the lease window and returns HTTP 200 with PROCESSING_IN_PROGRESS / alreadyProcessed: true. The invoice silently goes unprocessed for up to A1_LEASE_SECONDS (default 600s), and the flow may treat it as done.

Validate the body — sourceId, transport field present, base64 decodes, bytes non-empty — before the A1 claim. Bad requests then 400 without ever touching the ledger.

High

F2 · Invalid base64 is misreported as a CU failure (502)

base64.b64decode(content_b64) runs inside the try/except that maps every error to “Content Understanding analyze failed” (function_app.py:161–175). Worse, the default validate=False silently strips illegal characters, so corrupted input often decodes into garbage bytes that get sent to CU. There is also no guard for zero-byte content.

The flow passes a truncated or double-encoded payload → the caller sees “502 CU analyze failed” and debugs the wrong layer (per the project’s own debugging-discipline rule, the failing layer should be identified precisely).

Decode with validate=True in the validation block (with F1), return 400 “contentBase64 is not valid base64” / “content is empty”, and keep 502 exclusively for genuine CU failures.

High

H1 · Test harnesses silently test a different threshold than production

DEFAULT_FIELD_THRESHOLD = 0.75 is hardcoded in local_test.py:146 and verify_fn.py:108 and is always sent as fieldThreshold, overriding the Function. But the single source of truth is field_policy.THRESHOLD = 0.73 — which is what production sees, since the Power Automate flow sends no override. local.settings.json.template also says 0.75.

A field extracted at confidence 0.74 shows REVIEW in every harness scorecard but auto-writes (HAPPY_PATH) in production — test results systematically misrepresent deployed behavior, in the exact confidence band being tuned.

Both harnesses already import field_policy; default the CLI threshold to field_policy.THRESHOLD (keeping the static fallback when the import fails), and fix the template to 0.73. --field-threshold still overrides explicitly.

Medium

F3 · fieldThreshold accepts nonsense values without complaint

_field_threshold (function_app.py:61–75) accepts any float — 0, -3, 99 — and silently swallows unparseable values with no log line.

A flow variable bug sends fieldThreshold: 0 → every invoice becomes HAPPY_PATH_CANDIDATE and auto-writes to Dynamics with unvetted fields. Nothing in the response or logs flags it.

Reject values outside (0, 1] with a 400; log a warning when falling back from an unparseable value.

Medium

F4 · No timeout on the Content Understanding call

poller.result() in cu_client.py:115,127 waits indefinitely. A hung CU operation holds the invocation until the platform kills it, and the claimed row blocks reprocessing until the A1 lease expires.

Pass a timeout (e.g. poller.result(timeout=120)) so a hung analysis returns a clean 502 within the function’s lifetime.

Medium

F5 · Response claims “Extracted” even when the ledger write failed

When the post-CU ledger upsert fails (function_app.py:181–197), the response sets ledgerWriteError but still reports "status": "Extracted" — the ledger actually says Received.

The flow writes to Dynamics based on the decision, the ledger never records Extracted/decision stamps, and the row later resurfaces as “stuck” or gets resumed after the lease — a duplicate CU run for an invoice already written.

Report the truth: keep the decision payload but set status to reflect the failed write (e.g. "status": "Received" + ledgerWriteError), and document that the flow should route it to review. Exact contract is Decision 3.

Medium

D1 · .funcignore doesn’t exclude .venv / .python_packages

functionapp/.funcignore excludes tests and settings but not .venv/ or .python_packages/ — and functionapp/.venv exists on this machine. A func publish can package hundreds of MB of interpreter into the upload (remote build then ignores it, but upload time and package bloat are real).

Add .venv/, .python_packages/, and __azurite_db* patterns to .funcignore.

Low

D2 · README documents scripts that no longer exist

README.md lists step21_test.py and step24_test.py in the layout and tells readers to run step24_test.py; both were deleted in 1414f19. It also omits create_analyzer.py and tests/test_harness_scorecard.py, and its Security section (“never in a tracked .py”) is contradicted by S1. Long step24-comparison docstrings in local_test.py describe a divergence (CATEGORY_CRITICAL_FIELDS) that no longer exists.

Update README layout + harness examples + security note alongside the removals; trim the stale step24 docstring passages in files already being touched. No churn elsewhere.

Low

L1 · Accepted-risk items — flag, don’t fix now

Three things reviewed and judged not worth changing at prototype volume, listed so they’re on the record: (a) ledger.upsert is a read-modify-write without ETag concurrency — the A1 insert claim covers the race that matters; (b) ExpiresAt is decorative — Table Storage has no native TTL, so ledger rows accumulate until a cleanup job exists; (c) cu_client builds a new client + credential per request — a modest cold-path latency cost. (d) .gitignore has a dead .code-workspace entry (the workspace file is intentionally tracked).

Part 5

Decisions I need from you

Before I start

  1. Git history purge? Rotating the key (Phase 1) is mandatory and sufficient to revoke access. Scrubbing history (git filter-repo + force-push) additionally removes the dead key strings but rewrites every commit hash. My recommendation: rotate only if the repo is private; purge as well if it is (or ever was) public.
  2. Keep a stuck-row probe? phase3_ledger_test.py --show-stuck is the only tool that lists in-flight/stuck ledger rows. I recommend removing the file anyway (Azure Storage Explorer / az storage entity query covers it); say the word if you’d rather I keep a slim show_stuck.py.
  3. Ledger-write-failure contract (F5): prefer "status": "Received" + ledgerWriteError (truthful, flow routes to review), or keep "Extracted" and only document the field? I recommend the truthful status.
