Logging & Monitoring — Design + Setup Runbook

Noble Invoice Processor · metrics, alerts, and step-by-step Azure portal setup · sized for 500–1,500 invoices/month

function app: func-invoiceprocess-westus CU resource: invoice-processing-dev-resource ledger: stinvoicedevwestus / InvoiceExtractProcessLog notify: georgetsang@noblehomes.ca

Design premise. At 500–1,500 invoices/month (≈17–50/day, occasionally a burst of ~10 dropped at once), traffic is far too low for percentage-based rules — one bad invoice is 100% of that minute. Every alert below therefore uses absolute counts, and the most dangerous failure mode is silence (see the 2026-07-16 incident: 8 invoices dropped with green flow runs). The whole setup costs roughly $1–2/month; telemetry volume at this scale stays inside the free ingestion grant.

2Foundation check — is telemetry flowing?

Do this once before creating any alert. Everything below happens at portal.azure.com.

  1. In the top search bar type func-invoiceprocess-westus and open the Function App.
  2. In the left menu find Application Insights (under Settings). It should say Application Insights is enabled and link to the component (also named func-invoiceprocess-westus). Click the link — this App Insights resource is where all queries and most alerts in this doc live. Consider pinning it to your portal dashboard (pin icon, top right of its Overview page).
  3. On the App Insights resource, open Live metrics (left menu, under Investigate). Upload a test invoice to SharePoint (or wait for a real one) — within seconds you should see the request tick through. This is the fastest "is it alive right now" view.
  4. Open Logs (under Monitoring), close the query-picker dialog, paste query 1 from §5 and press Run. After the next deployment (which includes the RUN_SUMMARY change) every invoice shows one summary row here.
Two changes shipped with this design (take effect at the next func azure functionapp publish func-invoiceprocess-westus --build remote):
  • Sampling disabled (host.json): adaptive sampling could silently drop the exact traces/exceptions rows you need. At ≤50 requests/day it saved nothing. (This was also why the diagnostics design distrusted App Insights as an evidence store.)
  • RUN_SUMMARY log line (function_app.py): one stable INFO line per invocation, at every exit path:
    RUN_SUMMARY sourceId=<guid> httpStatus=200 status=Extracted decision=HAPPY_PATH_CANDIDATE cuMs=23411
    status/decision mirror the response (- when absent); cuMs=-1 means CU was never reached. On a CU timeout, cuMs records the elapsed time at failure (≈100,000 = the timeout cap). Queries and the log alert key on this line.
Naming caveat. Dev's App Insights component and its Log Analytics workspace (DefaultWorkspace-…-WUS) were auto-created by the portal; the convention names (appi-invoice-dev-westus, log-invoice-dev-westus) are a future Phase-2 recreate (see docs/naming-convention.html). Alerts you create now are attached to the resource and would need to be re-pointed if the component is ever recreated — that's fine, don't wait for the rename.

3Function App metrics to watch

How to view: Function App → Monitoring → Metrics. Pick a metric from the Metric dropdown, set the time range (top right), and note the Aggregation each metric needs. Verified against the Flex Consumption metric set (the app runs on a Flex Consumption plan — some classic App Service metrics don't exist here).

Metric (aggregation)What it means for this app at 17–50 invocations/day
Requests (Sum) Total HTTP calls. Should track invoice volume (plus flow retries). A day at 0 while invoices arrived in SharePoint = dead pipeline (scenario S10).
Http5xx — "Http Server Errors" (Sum) Every failed invoice attempt: 502 = CU analyze failed/timed out, 500 = ledger/storage/decision failure. The single most important function metric → alert ALT-1.
Http4xx (Sum) Bad requests from the flow (malformed base64, missing sourceId) and 401/403 = a broken function key after key rotation. Normally 0.
HttpResponseTime — "Response Time" (Avg) End-to-end duration in seconds. Normal runs ~15–40 s (dominated by CU). Creep toward 100 s = CU degradation, and past ~120 s the Power Automate connector gives up → alert ALT-4 watches this from the App Insights side with more precision.
InstanceCount — "Automatic Scaling Instance Count" (Max) How many instances Flex spun up. Per-instance concurrency is 1 here, so a burst of 8 simultaneous drops = 8 instances. Useful when analyzing burst incidents (S1).
CpuPercentage / MemoryWorkingSet (Avg) Resource pressure per instance. This workload is I/O-bound (waiting on CU), so sustained high CPU/memory would be anomalous.
OnDemandFunctionExecutionCount (Sum) Billing meter: executions on on-demand instances. Sanity-check against invoice volume. AlwaysReadyFunctionExecutionCount stays 0 (no always-ready instances configured — that's why first invocations after idle take a few seconds longer: cold start, 2–6 s, worst ~10 s).
Platform metrics vs App Insights. The metrics above come from the hosting platform (they'd exist even with App Insights off). Function-level detail — which stage failed, stack traces, per-invoice timing — lives only in App Insights (§5). Also note: on Flex Consumption, don't rely on Diagnostic settings/FunctionAppLogs; App Insights is the supported logging path. The Function App's Diagnose and solve problems blade has two Flex-specific tools worth knowing: search for Flex Consumption Deployment (deployment history/status) and Flex Consumption Quota (regional instance quota).

4Content Understanding metrics to watch

How to view: portal search → invoice-processing-dev-resource → left menu Monitoring → Metrics. Useful trick: after picking a metric, click Apply splitting → OperationName to see which API operation the numbers belong to (one invoice produces several calls: the analyze POST plus result-polling GETs, so TotalCalls is a multiple of invoice count).

Metric (aggregation)What it means here
TotalCalls / SuccessfulCalls (Sum) All HTTP calls to the resource. Baseline first, then watch for shape changes.
ServerErrors (Sum) 5xx from the CU service itself → alert ALT-2. A burst here alongside function 502s says "the service, not your code".
ClientErrors (Sum) 4xx — after a deployment, a spike here means a broken request (bad analyzer id, auth, malformed payload), not a CU outage.
BlockedCalls (Sum) Calls rejected for rate/quota (429). S0 limits are 1,000 pages/min and 3,000 operations/min — unreachable at this volume, so any blocked call means a runaway loop or another consumer on the resource → alert ALT-3.
Latency (Avg) Caveat: this measures each HTTP call, and analyze is a long-running operation — the POST returns fast (202) and the polls are fast, so this metric does not reflect end-to-end analyze time. The true end-to-end signal is cuMs in RUN_SUMMARY (§5 query 3) and CuDurationMs on the ledger row. Use Latency only for gross anomalies.
SuccessRate — "AvailabilityRate" (Avg) (TotalCalls − ServerErrors)/TotalCalls as %. Fine for a dashboard tile; too coarse to alert on at this volume.
ProcessedDocumentPages — "Processed Pages" (Sum) This is what CU bills on. Month-to-date pages should track invoice volume (invoices here are 1–3 pages). A jump without a volume jump = someone feeding big documents or a reprocessing loop.
Tokens (Sum) Generative-model token usage by the analyzer's generate fields. Watch the trend after prompt changes to the analyzer.

5KQL query pack (App Insights → Logs)

How to run: App Insights resource → Monitoring → Logs → close the picker dialog → paste a query → Run. Set the time range with the Time range button or keep the ago(…) in the query. Save favorites with Save → Save as query so they're one click next time.

Query 1 — per-invoice run table (the workhorse)

traces
| where timestamp > ago(7d)
| where message startswith "RUN_SUMMARY"
| parse message with "RUN_SUMMARY sourceId=" sourceId " httpStatus=" httpStatus:int
                     " status=" status " decision=" decision " cuMs=" cuMs:long
| project timestamp, sourceId, httpStatus, status, decision, cuMs
| order by timestamp desc

One row per invocation: outcome, routing decision, CU duration. Filter it, e.g. append | where httpStatus >= 500 for failures only, or | where decision == "PROCESSING_IN_PROGRESS" to see A1 short-circuits (retries that arrived while another run held the claim).

Query 2 — daily volume and outcome mix

traces
| where timestamp > ago(30d)
| where message startswith "RUN_SUMMARY"
| parse message with "RUN_SUMMARY sourceId=" sourceId " httpStatus=" httpStatus:int
                     " status=" status " decision=" decision " cuMs=" cuMs:long
| summarize runs = count(),
            failed = countif(httpStatus >= 500),
            happy = countif(decision == "HAPPY_PATH_CANDIDATE"),
            review = countif(decision startswith "REVIEW"),
            reject = countif(decision startswith "REJECT")
          by bin(timestamp, 1d)
| order by timestamp desc

Watch the mix: a drift where review/reject climbs while volume is flat = CU extraction quality regressing (scenario S9) — investigate with scripts\diag.py before touching thresholds (classify labels are noisy run-to-run; never conclude from one document).

Query 3 — CU duration trend vs the 100 s cap

traces
| where timestamp > ago(30d)
| where message startswith "RUN_SUMMARY"
| parse message with "RUN_SUMMARY sourceId=" sourceId " httpStatus=" httpStatus:int
                     " status=" status " decision=" decision " cuMs=" cuMs:long
| where cuMs >= 0
| summarize p50 = percentile(cuMs, 50), p95 = percentile(cuMs, 95), max(cuMs)
          by bin(timestamp, 1d)
| render timechart

The early-warning chart. CU is capped at 100 s (AZURE_CU_TIMEOUT_SECONDS); p95 drifting from ~30 s toward 60–80 s means timeouts are coming, especially under burst (the 2026-07-16 incident was exactly this under 8 concurrent analyzes).

Query 4 — failed requests with response codes

requests
| where timestamp > ago(7d)
| where success == false
| project timestamp, name, resultCode, duration, operation_Id
| order by timestamp desc

Click any row → open the end-to-end transaction view to see every log line and exception of that invocation, correlated by operation_Id.

Query 5 — exceptions with stack traces

exceptions
| where timestamp > ago(7d)
| project timestamp, type, outerMessage, method, operation_Id
| order by timestamp desc

Query 6 — known warning signatures

traces
| where timestamp > ago(30d)
| where message startswith "Diagnostics blob write failed"
     or message startswith "Failure release lost the etag race"
| project timestamp, message, severityLevel, operation_Id

The first = the best-effort sidecar failed (an Extracted row with empty blob paths — check storage RBAC). The second = a failure release lost to a newer claim (benign one-off; frequent = investigate).

Query 7 — cold starts (new instances)

requests
| where timestamp > ago(7d)
| summarize firstRequest = min(timestamp), requests = count() by cloud_RoleInstance
| order by firstRequest desc

Each row is an instance Flex created; its first request paid the cold start (2–6 s). Many instances in one minute = a burst fan-out.

Why no dependencies queries? Python Functions don't auto-collect outbound dependency telemetry (that needs OpenTelemetry — deliberately deferred, see §10). The dependencies table will be empty; cuMs in RUN_SUMMARY is the CU timing signal instead.

7Alerts — step-by-step setup

Concepts in one paragraph: an alert rule = a scope (which resource) + a condition (signal and threshold) + an action group (who gets notified). Severity is just a label (0 Critical … 4 Verbose); this doc uses 2 for "act today" and 3 for "informational". Metric alert rules cost ~$0.10/month each (first 10 signals free), the one log-search alert ~$0.50/month.

7.1 Create the action group (once)

  1. Portal top search → Monitor → left menu Alerts → Action groups → + Create.
  2. Basics: Subscription dev-Document Intelligence; Resource group rg-content-understanding-dev; Region: Global; Action group name ag-invoice-dev-email; Display name InvoiceDev (this prefix appears in the email subject, max 12 chars).
  3. Notifications tab: Notification type Email/SMS message/Push/Voice → tick Email → enter georgetsang@noblehomes.ca → OK. Name the notification email-george.
  4. Skip Actions (that's for webhooks/automation) → Review + create → Create.
  5. Verify: open the new action group → Test action group (top bar) → sample type Metric alert → Test. An email should arrive within a couple of minutes (check spam once; Azure alert mail comes from azure-noreply@microsoft.com).

7.2 ALT-1 — Function failures (Http 5xx)

  1. Open func-invoiceprocess-westus → left menu Alerts (under Monitoring) → + Create → Alert rule. The scope is pre-selected to the function app.
  2. Condition tab: Signal name → search and pick Http Server Errors. Threshold: Static; Aggregation type: Total; Operator: Greater than or equal to; Threshold value: 3. Under When to evaluate: Check every 15 minutes, Lookback period 1 hour.
  3. Actions tab: Select action groups → tick ag-invoice-dev-email.
  4. Details tab: Severity 2 — Warning; Alert rule name alert-invoice-func-5xx; Description: "3+ failed invoice attempts in an hour — see monitoring-design.html S1/S6". Leave Automatically resolve alerts checked.
  5. Review + create → Create.
Why ≥3 per hour? One failing invoice triggers the flow's automatic retries (up to 4 over ~16 min), so a single transient CU blip can produce 1–2 5xxs that recover on their own. Three or more inside an hour is either one invoice whose retries are exhausting (you'll also get the §8.2 flow email) or several invoices failing — both worth reading immediately.

7.3 ALT-2 — Content Understanding server errors

  1. Open invoice-processing-dev-resource → Alerts → + Create → Alert rule.
  2. Condition: Signal Server Errors; Static; Aggregation Total; Operator Greater than or equal to; Threshold 3; Check every 15 minutes; Lookback 1 hour.
  3. Actions: ag-invoice-dev-email. Details: Severity 2; name alert-invoice-cu-5xx.
  4. Review + create.

7.4 ALT-3 — Content Understanding throttling (should never fire)

  1. Same resource, + Create → Alert rule.
  2. Condition: Signal Blocked Calls; Static; Aggregation Total; Operator Greater than or equal to; Threshold 1; Check every 5 minutes; Lookback 15 minutes.
  3. Actions: ag-invoice-dev-email. Details: Severity 3; name alert-invoice-cu-throttle.

7.5 ALT-4 — latency creep (log-search alert)

  1. Open the App Insights resource → Logs; paste: 
    requests
| where duration > 60000
  2. Click + New alert rule (toolbar above the query).
  3. Condition is pre-filled with the query. Set: Measurement — Measure Table rows, Aggregation granularity 1 hour. Alert logic: Operator Greater than or equal to, Threshold value 2, Frequency of evaluation 15 minutes.
  4. Actions: ag-invoice-dev-email. Details: Severity 3; name alert-invoice-slow-runs; description "2+ runs over 60 s in an hour — CU latency creeping toward the 100 s cap (S8); check monitoring-design.html §5 query 3".
  5. Review + create. (This is the one ~$0.50/month rule.)

7.6 ALT-5 (optional) — exception burst

Largely overlaps ALT-1 (most exceptions end as 5xx responses), but it also catches failures that didn't surface as HTTP errors (e.g. the ledger-divergence path S4 returns 200). If you want it: App Insights resource → Alerts → + Create → signal Exceptions → Static, Total, ≥ 5, check every 15 min, lookback 1 hour → action group → Severity 3 → name alert-invoice-exceptions.

8The ledger reconciliation flow (the silent-drop backstop)

Azure alerts can't see the ledger table, and nothing Azure-side can prove "every invoice that arrived was processed". This scheduled Power Automate flow automates runbook §10 — it is the single most important item in this document, because it catches every failure class, including the ones that leave no telemetry at all.

  1. make.powerautomate.com → + Create → Scheduled cloud flow. Name Invoice ledger reconciliation; run daily at 08:00 (after the typical morning batch) → Create.
  2. + New step → search connector Azure Table Storage → action Get entities (V2) (the exact label can vary slightly by connector version — any "get/list entities" action works). Creating the connection asks for: display name stinvoicedevwestus, Storage account name stinvoicedevwestus, and a Shared Storage Key — portal → stinvoicedevwestus → Security + networking → Access keys → Show → copy key1. note If access keys are disabled on the account ("Allow storage account key access" = Disabled), either enable shared key or use an HTTP action with Entra auth — check before building.
  3. In the action: Table InvoiceExtractProcessLog. Open Advanced parameters → Filter Query and paste (one line): 
    (Status eq 'Received' or Status eq 'Failed') and IngestedUtc lt datetime'@{formatDateTime(addHours(utcNow(), -2), 'yyyy-MM-ddTHH:mm:ss')}Z'
    The @{…} part is a Power Automate expression (paste into the field as-is; it renders as a purple token): "two hours ago", well past the 300 s A1 lease, mirroring runbook §10. Phase 4 Once the Dataverse write is live, also catch Extracted-but-never-Written rows by extending the filter with or (Status eq 'Extracted' and DynamicsRecordId eq '') — mind the duplicate-row caution in runbook §10 before resubmitting those.
  4. + New step → Condition: left value = expression length(outputs('Get_entities_(V2)')?['body/value']) (adjust the action name token to what the designer shows) · is greater than · 0.
  5. In the If yes branch: Create HTML table (Data Operations) with From = the entities list output; then Send an email (V2) (Office 365 Outlook) → To georgetsang@noblehomes.ca; Subject ⚠ Invoice reconciliation: stuck rows found; Body: the HTML table output plus a link to this doc. Leave If no empty (silence = all clear). Optionally add a Teams "Post message" action later.
  6. Save, then Test → Manually once. To verify the alarm path end-to-end, temporarily change -2 hours to -2000 (matches old Failed test rows), run, confirm the email, then change it back.

8.2 Flow-failure notification on the main flow (Phase 5 item)

Since the 2026-07-16 fixes, real failures surface as Failed runs of the main flow (after the 4×PT4M retries exhaust). By default you'd only notice by opening run history. Add an explicit email:

  1. Edit the main invoice flow. After the Process invoice action (or around the whole post-trigger logic), add a Scope if you prefer grouping; simplest version: add a Send an email (V2) action at the end of the flow, in parallel or below.
  2. On that email action open … → Configure run after → tick has failed and has timed out (untick is successful) → Done. It now runs only when the preceding step failed.
  3. Email: To georgetsang@noblehomes.ca; Subject ⚠ Invoice flow failed: @{triggerOutputs()?['body/{FilenameWithExtension}']}; Body: include the file name, link to the run (@{workflow()?['run']?['name']}), and "see monitoring-design.html §9".
  4. Save. Also double-check the retry policy is still set on the Process invoice action (Settings → Retry policy: Fixed, 4 × PT4M) — it is load-bearing (see the incident doc); PT2M silently breaks the recovery path at the current 300 s lease.

9Troubleshooting walkthrough — "an invoice didn't arrive"

  1. Power Automate run history (the flow → 28-day run history): find the run for the file. No run at all → trigger/connection problem (S10): check the flow is On and connections valid. Run Failed → open it, read the Process invoice action's response body.
  2. Ledger row — portal → stinvoicedevwestus → Storage browser → Tables → InvoiceExtractProcessLog → filter FileName eq the file name. Read Status / RoutingDecision / FailedStage / LastError — this usually ends the diagnosis (interpretation table: diagnostics runbook §3, §10).
  3. App Insights detail — Logs → §5 query 1 filtered: | where sourceId == "<RowKey>" for the run-by-run history, then query 4/5 by timestamp → end-to-end transaction view for stack traces.
  4. Field-level forensics — .\.venv\Scripts\python.exe scripts\diag.py --source-id <guid> for the raw CU result + decision JSON (diagnostics runbook §3–§6).
  5. Fix and resubmit — per runbook §10: past the lease, resubmitting the flow run (or re-uploading the file) re-claims and re-processes cleanly.

10Deliberately deferred

  • Availability (ping) test — needs a side-effect-free /api/health endpoint first (the only route today, POST process-invoice, writes the ledger). Note: classic URL ping tests retire 2026-09-30; use a Standard test when this is added.
  • OpenTelemetry / customDimensions / dependency tracking (HG-05 family) — adds a dependency and config; RUN_SUMMARY text-parsing covers today's needs.
  • functionTimeout and concurrency caps in host.json (HG-11) — separate hardening decision, not a monitoring change.
  • App Insights / workspace rename to appi-invoice-dev-westus / log-invoice-dev-westus — Phase-2 recreate; re-point the App-Insights-scoped alerts (ALT-4/5) afterwards.
  • Timer-based ledger metrics — superseded by the §8 reconciliation flow (user decision, 2026-07-17).
